# メール取込の複数アカウント化とLLMコスト制御（denylist方式の推奨）

## Summary

- メール取込の複数アカウント対応は**設定上すでに可能**（`SesMailImportProperties` が `List<Account>` を保持。ymlに追記するだけ）
- 取込の前段機械判定は**バウンス検知（BounceDetector）のみ**。それ以外は全通LLMに投げ、案件/要員/その他の分類自体をLLMが行う（`classified_by=LLM`）
- 案件受信用でない混在アドレスを追加すると、その他メール1通ごとにフル抽出1回分（約6,000トークン）のコストが発生する。金額は軽微（1通数円以下）だが、**TPM天井（毎分約33リクエスト）を無関係メールが浪費して取込時間が延びる**のが実害
- ノイズ対策のリスト運用は**ホワイトリスト方式ではなくdenylist方式を推奨**（2026-08-24 人間合意）:
  - ホワイトリスト方式（実績ドメインのみLLMへ・リスト外スキップ）は、**新規取引先の初回メールが「スキップ→分類されない→実績が付かない→永遠にリスト外」のループに嵌まる**構造的取りこぼしを生む。SESは新規送信元が増え続ける業態（実績98ドメインは全部かつて新規）
  - denylist方式（リスト外はLLMへ＝発見経路維持・「その他しか送らない」実績ドメインだけ弾く）なら誤差ゼロのまま定常ノイズだけ止められる。弾いた分も原本は mails 保存（バウンスと同じ `KIND_OTHER`/`CLASSIFIED_BY_RULE` パターン）にすれば誤除外を後から救済できる

## Verbatim

dev DB実測（2026-08-24・mails全5,351通超時点）:

```
案件/要員を送ってきたドメイン数: 98（メール4,172通）
その他のみのドメイン数: 37（メール2,061通）
両方送ってくるドメイン数: 7（その他側はわずか14通）
その他メールの最多送信元: mailer-daemon 1,627通（バウンス＝ルール処理済み・LLM未呼び出し）
→ LLMを実際に呼んでいる「その他」は約450通規模
```

- ドメインと内容の分離は綺麗（混在7ドメイン・14通のみ）→ ドメイン単位のリスト運用で精度誤差は実質出ない
- コード上の分岐: `MailImportRecordService.java` — `KIND_PROJECT=0 / KIND_STAFF=1 / KIND_OTHER=2`、
  `CLASSIFIED_BY_RULE=0`（バウンスのみ）/ `CLASSIFIED_BY_LLM=1`（それ以外全部）。
  `MailImportService.java:315` `BounceDetector.isBounce(mail)` がLLM前の唯一の機械フィルタ

## Usage

- 複数アカウント化を実施するときの設計前提（起票時にこの知見をタスクへ転記する）
- 運用側は対象アドレスへ案件情報を集中させる方針（2026-08-24時点）。まずメールサーバー側振り分け（フォルダ購読）で受け、足りなければdenylistを実装する順
