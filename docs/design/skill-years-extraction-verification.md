# スキル経験年数のLLM抽出 精度検証（decision-log #22 判定利用の検討用）

実施日: 2026-08-18／構成: 採用抽出構成と同一（gpt-5.6-luna・Structured Outputs）に `skill_years` 配列を追加
対象: 検証済み実メールデータセット（v3c）の project 分類 171通（ローカル保管・リポジトリ外）

## 1. 方法

- 商流・年齢検証（[精度検証](flow-age-extraction-verification.md)）と同方式の派生スクリプトで、案件抽出スキーマに
  `skill_years[] = { skill_text（スキル名・非特定はnull）, min_years（最低年数）, source_text（根拠原文）, kind（required/preferred/overall） }` を追加して全171通を抽出
- 正規化ルールをプロンプトに事前定義: 「5年以上」「5年〜」→5／「3〜5年」→下限の3／「1年半」→1.5／数値のない表現（「経験豊富」等）→null＋原文保持／要員紹介側・社歴・稼働時期の年数は対象外
- 評価は3段: ①正規表現プレスキャン（「N年」＋経験/実務/歴の同一行）との突き合わせ ②全エントリの目視レビュー ③source_text が本文に逐語一致するかの機械照合（全件）

## 2. 結果サマリー

| 指標 | 結果 |
|---|---|
| 記載のあるメール（実態） | 約75/171通（44%）。商流58%・年齢50%と同水準 |
| 抽出 | 74通・117エントリ（required 97 / preferred 3 / overall 17） |
| 根拠原文の正当性（捏造・誤引用） | **0件**（117/117が本文に逐語一致。機械照合） |
| 実質的な取りこぼし | **0件**。プレスキャン候補17通は精査の結果、日付＋「経験」の誤ヒット・年数なし・要員側年数の正当な棄却。残る1通（混在スレッド）は分類段で staff 判定になったもので年数抽出の問題ではない |
| 正規化の一貫性 | 範囲の下限採用・「程度/目安」→数値・数値なし→null すべて一貫。原文の脱字もそのまま逐語抽出（要約なし） |
| 揺れ（軽微） | スキル非特定の総合経験が required(skill_text=null) と overall で1組不一致 → 利用側で「skill_text=null は overall 扱い」に正規化すれば実害なし |

- 追いコスト: 1通あたり出力 +約0.5k トークン（既存抽出への項目追加のため増分は出力側のみで僅少）
- 「3年以上あると面談に進みやすい」のような尚可側の年数も kind=preferred で正しく分離できた

## 3. 設計へのフィードバック

- 表現の実態は「以上」だけでなく**「目安」「程度」「〜レベルは欲しい」が相当数**。年数のハード足切りは実態より厳しくなりやすく、プロトタイプ流儀の**OK/NG＋理由表示（または不足時の減点）**が適合する
- 判定不能（案件側記載なし・要員側の年数未入力）は通過させる（商流・年齢フィルタと同じ思想）
- `skill_text` は原文表記のため、判定にはスキルマスタ（skill_id）への解決が必要。実装時は既存のスキルタグ紐付けパイプラインに乗せる
- 判定に使うなら kind=required のみを対象とし、preferred / overall は表示・参考扱いが安全

## 4. 結論

- 抽出精度は実用水準（捏造0・実質取りこぼし0・正規化一貫）。**#22の「判定利用」は技術的に成立する**
- 採否と判定方式（ハードフィルタ／減点／表示強化のいずれか）は人間と相談のうえ決定する（本検証はその判断材料）
- 検証スクリプト・結果はローカル保管（実メールデータのためリポジトリには含めない）
