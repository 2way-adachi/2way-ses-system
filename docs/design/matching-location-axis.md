# マッチング location軸（勤務地の地方判定） 設計

作成: 2026-08-19（人間指示起点）
関連決定: #34

---

## 1. 目的と背景

条件適合の判定は8軸（price / startDate / age / workStyle / commercialFlow / nationality / freelancer / skillYears）で構成しており、
勤務地（`location`）は「初期版では自動判定せず、案件側の場所と要員側の希望エリアを画面表示して営業担当が判断する」としていた。

しかしこの前提には穴がある。`workStyle` 軸（`MatchScoreCalculator.workStyle`）はリモート希望のみを見ており、
地理を一切見ていない。そのため次の組み合わせが **workStyle = OK で通過する**。

| 案件 | 要員 | 現状の判定 | 実際 |
|---|---|---|---|
| 関東・常駐 | 関西在住・出社のみ可 | OK（通過） | 通勤不可能 |

関西から関東へのフル出社は成立しないため、フルリモート案件を例外として地方の一致判定を入れ、
別地方の組み合わせは候補から除外する。

---

## 2. 判定材料の実態（2026-08-19 開発環境の実測）

### 2.1 案件側 `projects.location`

1454件中、記載ありが大半。中身は自由文で、駅名・地名・リモート表現・注記が混在する。

| 分類 | 件数 | 比率 |
|---|---|---|
| 都道府県名を含む | 151 | 10.4% |
| 23区名・政令市名・「都内」等を含む | 304 | 20.9% |
| フルリモート表現で決着 | 141 | 9.7% |
| 裸の駅名（辞書が必要） | 858 | 59.0% |

裸の駅名の異なり語は245語で、**上位200語で94.8%をカバー**する。

`remote_type` の分布は フルリモート138 / 併用647 / 常駐529 / 不明24（1338件時点の計測）。

### 2.2 要員側

- **メンバー（`personnel`）**: 決定#32の移設により `prefecture`・`city`・`preferred_location`・`remote_preference` を保持する。
  実データは11件中10件で `prefecture` が充足（東京都7・神奈川県2・埼玉県1）。`preferred_location` は自由文
  （`一都三県`／`東京都内、リモート週2以上`）
- **要員候補（`staff_candidates`）**: 都道府県カラムを持たず、判定材料は `nearest_station` のみ。
  899件中、県名を含むものが14.9%、区市名が5.9%、**裸の駅名が79.2%**（異なり語275語）。
  構造的にメンバー側より精度が落ちる

## 3. 地方区分

8地方区分とし、一致を必須とする。

| 区分 | 都道府県 |
|---|---|
| 北海道 | 北海道 |
| 東北 | 青森・岩手・宮城・秋田・山形・福島 |
| 関東 | 茨城・栃木・群馬・埼玉・千葉・東京・神奈川 |
| 中部 | 新潟・富山・石川・福井・山梨・長野・岐阜・静岡・愛知 |
| 関西 | 三重・滋賀・京都・大阪・兵庫・奈良・和歌山 |
| 中国 | 鳥取・島根・岡山・広島・山口 |
| 四国 | 徳島・香川・愛媛・高知 |
| 九州沖縄 | 福岡・佐賀・長崎・熊本・大分・宮崎・鹿児島・沖縄 |

「関東・関西・その他」の3分類ではなく8区分を採る理由は、実データに愛知・岐阜・石川・宮城・福岡の案件が存在し、
3分類だと「その他」同士（例: 愛知案件 × 福岡在住）が一致扱いで通過してしまうため。

三重を関西に含めるのは、SES商流で名古屋圏と大阪圏の双方に通勤圏が跨るため運用上の便宜による。
誤判定の方向は「除外しすぎない」側に倒す方針（§6）と整合する。

## 4. 判定仕様

`location` を9軸目として `conditionChecks` に追加する。上から評価し、最初に該当した行で確定する。

| # | 条件 | 結果 |
|---|---|---|
| 1 | `location` に否定キーワード（`地方不可`・`フルリモート限定は対象外` 等）を含む | 地方一致を必須とし、不一致は **NG** |
| 2 | 案件が `remote_type = 0`（フルリモート） | **OK**（例外。地理を見ない） |
| 3 | 案件が `remote_type = 1`（併用）かつ低頻度出社キーワードを含む | 不一致なら **WARNING** |
| 4 | 案件側・要員側のいずれかで地方が特定できない | **OK** ＋ 理由「判定材料なし」 |
| 5 | 地方が一致 | **OK** |
| 6 | 地方が不一致 | **NG** |

NGが1件でもあると候補一覧から除外される既存仕様（`MatchScoreCalculator.hasNg`）にそのまま乗るため、
「別地方は除外」は追加の仕組みなしで実現される。WARNINGは `conditionFactor` を通じてスコアを下げる。

### 4.1 否定キーワードを最優先にする理由

低頻度出社の案件であっても地方在住を明示的に断っているものが実在する。

- `基本リモート（参画時に豊洲出社あり／地方不可）`
- `基本テレワーク（チームMTG・顧客打合せ時に出社あり。フルリモート限定は対象外）`
- `フルリモート※地方不可`

否定キーワードの判定を #2・#3 より後ろに置くと、これらが誤ってOK／WARNINGで通過する。

### 4.2 低頻度出社キーワード

`基本リモート`・`原則リモート`・`基本テレワーク`・`月1`・`リモート主体`・`ほぼリモート` 等。
併用722件のうち該当は57件（7.9%）で、残る92%は地方不一致ならNGとなる。

### 4.3 要員側の地方の解決順

| 対象 | 解決順 |
|---|---|
| メンバー | `prefecture` → `preferred_location` → `nearest_station` |
| 要員候補 | `nearest_station` のみ |

### 4.4 複数地名の併記

`六本木一丁目駅or金沢駅` のように複数地名を併記する案件は、**いずれか1つが要員の地方と一致すればOK**とする。

## 5. 辞書の作り方

取込済みデータから語彙を起こす。全国駅マスタの導入やLLM抽出は採らない
（前者は同名駅の解決ルールとマスタ更新運用が別途必要、後者は「都度コストが発生する機能を先に実装しない」方針に反する）。

初期辞書は次の構成で、規模はおよそ300語。

1. 都道府県名47語（「県」「府」「都」の有無いずれも受ける）
2. 東京23区名・政令指定都市名・「都内」「一都三県」等の広域表現
3. 既存の `projects.location` と `staff_candidates.nearest_station` に実際に出現する駅名の上位語

未知語は §4 の #4 に落ちて「判定材料なし＝OK」となるため、辞書の穴が誤除外を生むことはない。

---

## 6. 同名地名の扱い

同じ地名が複数の地方に存在するものは、まず実データの中身を確認し、
**一意に決まるものは根拠付きで倒し、真に曖昧なものだけ辞書から除外して「判定材料なし」に落とす**。

| 地名 | 頻度 | 実データの中身 | 判断 |
|---|---|---|---|
| 府中 | 60 | 全て東京都府中市。広島県府中市は0件 | 関東に倒す |
| 橋本 | 35 | `京王線 橋本駅`＝神奈川県相模原市。福岡・和歌山は0件 | 関東に倒す |
| 大手町 | 14 | 全て東京。福岡市の大手町は0件 | 関東に倒す |
| 大和 | 10 | `相鉄線・小田急線 大和駅`＝神奈川県大和市。奈良は0件 | 関東に倒す |
| 本町 | 8 | `大阪・本町` 等で大阪。`岩本町`（東京）は別トークン | 関西に倒す |
| 三田 | 6 | `都営三田`＝東京都港区。兵庫県三田市は0件 | 関東に倒す |
| 淡路 | 5 | 候補側 `阪急 淡路駅`＝大阪。`淡路町`（東京）は別トークン | 関西に倒す |
| 福島 | 6 | 大阪市福島区だが福島県と完全同名 | **除外** |
| 山手 | 5 | 横浜の山手駅と `山手線`（路線名）が混在 | **除外** |

判断の拠り所は非対称性にある。誤NGは提案機会の損失に直結し、しかも候補一覧から消えるため人間が気付けない。
誤OKは一覧に残るので営業担当が弾ける。**迷ったら誤OK側**、すなわち除外＝判定材料なしに倒す。

実データ根拠で倒した7語は、将来その地方以外の案件が来た時点で誤判定する。定期的な見直しが要る。

### 6.1 辞書引きは部分一致を禁止する

トークン完全一致で引く。部分一致にすると `岩本町`（東京）が `本町`（大阪）に、
`大和田`（埼玉）が `大和`（神奈川）に、`山手線`（路線名）が `山手`（横浜）にヒットして全て誤判定する。
前処理（括弧・注記の除去、区切り文字での分割、`駅`等の接尾辞と路線名の接頭辞の除去）の詳細は実装タスクを参照。

## 7. 正規化結果の保持

案件側は `projects.region` を追加し、メール取込時に辞書で判定して保存する。
既存分は `POST /ses/mail-import/skill-years-backfill` と同型のバックフィルAPIで一括更新する。

要員側は都度導出とする（`prefecture` からの導出は1回の辞書引きで済むため、カラムを増やす価値がない）。

## 8. 影響範囲

### 8.1 DB

- `projects` に `region` を追加（`docs/ddl/schema-ses.sql`）
- 既存案件のバックフィル

### 8.2 thyme / lemongrass

| ファイル | 変更 |
|---|---|
| `internal/MatchScoreCalculator.java` | `location` 軸の判定メソッド追加。`countStatus` の集計配列に `location` を追加（追加漏れると軸が集計されない） |
| `entity/ConditionChecksData.java` | `location` フィールド追加 |
| `entity/MatchSubjectData.java` | 要員側の地方解決に必要な項目を追加 |
| `entity/CandidateProjectData.java` | 案件側の `region` を渡す |
| `internal/MatchComparisonBuilder.java` | 対比表に location 行を追加 |
| `service/ProjectService.java` | 候補一覧の評価に軸を追加 |
| 地名辞書クラス（新規） | 地名文字列 → 地方コードの解決 |

### 8.3 Lavender

マッチング結果画面（決定#30）の条件対比表に location 行を追加する。

### 8.4 スナップショット互換

`match_snapshot(v2)` は `skillYears` 追加時と同じ扱いとし、本軸の追加より前に保存されたスナップショットは
`location` キーを持たない（読み取り時 null、ビュー側は NON_NULL で省く）。既存データの移行はしない。

## 9. 実装の前提

個人属性移設（決定#32・#33）の**手順5（thyme の読み取り経路切り替え）と同時に実施する**。
手順5は `MatchSubjectData.of(Personnel, ...)` を `personnel` 直読みへ切り替える工程であり、
本軸が要員側の判定材料を取る場所とまったく同じ。別々に進めると同一ファイルを2度触ることになる。
