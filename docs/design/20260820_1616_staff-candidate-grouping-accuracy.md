# 要員候補の名寄せ 精度検証（2026-08-20）

決定#35で導入した要員候補（`staff_candidates`）の名寄せグルーピングについて、
dev DBの実データで判定基準と結果を検証した記録。
案件側の [同一案件グルーピング 精度検証](20260819_1717_project-grouping-accuracy.md) と対になる。

## Summary

**確定した判定基準: イニシャル一致 ＋ 最寄駅トークン交差 ＋ 年齢一致（両方非NULLのときのみ）の3条件AND**

- 実データ1,047件 → **439グループ**（約58%圧縮）。うち262グループは1件のまま
- **誤統合0件**。実装の判定ロジックを移植して全グループの全ペアを検査し、
  条件を満たさない同居が1件も無いことを確認した（後述の定量化を参照）
- **畳み損ね4件**。別グループの代表同士で条件を満たすペアが4組ある。
  判定条件の問題ではなく、取込時付与とバックフィルの実行順が混ざったことによる経路差
- `affiliation`（所属）はキーに使わない。入れると**53グループ余計に割れる**（1,047件時点の再測定値。
  決定#35の記載は996件時点の44グループ）
- 案件側と異なり、**イニシャルまたは最寄駅が空のレコードは畳まない**（安全側に倒す）

## Verbatim

### 検証条件

- 対象: `ses.staff_candidates` 全1,047件（`group_id` は2026-08-20のバックフィル済み）
- 判定ロジックは `StaffCandidateGroupKeyResolver.isSameGroup()` と
  `LocationDictionary.tokenize()` をPythonへ移植して再現。処理順は実装と同じ
  「受信の古い順に逐次処理し、既存グループの代表とだけ照合する」方式

### 条件別のグループ数

```
条件                                     グループ数
イニシャルのみ                                195
＋最寄駅（生文字列の完全一致）                   448
＋最寄駅（正規化トークン交差）                   433
＋最寄駅（正規化）＋年齢【現行の判定】             435
＋最寄駅（正規化）＋年齢＋所属                   488
```

読み取れること:

- **イニシャルだけでは畳みすぎる**（195グループ）。`T.M` `K.M` のような2文字イニシャルは衝突が多い
- **最寄駅の正規化は効く**（448→433。15グループぶん）。`京王線 橋本駅` と `橋本駅` のような
  路線名・接尾辞の差を吸収する
- **年齢は2グループを正しく分離する**（433→435）。同一イニシャル・同一駅の別人を分ける唯一の材料
- **所属を入れると53グループ余計に割れる**（435→488）。同一人物でも営業ごとに表記が違うため

### 所属をキーに使えない理由（実データ）

同一グループ内に共存している所属表記の例:

```
group 28 (8件): 弊社社員(株式会社ギグー) / 弊社社員(株式会社ギグーのプロパー) /
                株式会社ギグー プロパー(弊社社員) / 株式会社ギグー(自社社員) /
                自社社員 / 自社社員(株式会社ギグー)
group 15 (7件): 弊社正社員(株式会社ギグー) / 株式会社ギグー 正社員 /
                株式会社ギグー正社員 / 自社正社員
group 22 (7件): 弊社グループ会社正社員 / 弊社グループ会社正社員 ※ご契約時直接契約可 /
                弊社グループ会社正社員(ご契約時直接契約可) / 弊社グループ会社正社員(契約時直接契約可)
group 11 (4件): 一社先正社員 / 一社先正社員(弊社懇意企業要員) /
                一社先正社員(弊社懇意企業要員・独占営業中)
```

所属が複数種になっているグループは177グループ中32。括弧内の注記・「弊社/自社」の揺れ・
社名の有無が入り混じり、正規化で寄せきれない。

### 誤統合と畳み損ねの定量化

全439グループについて、実装の判定ロジックで検査した結果:

```
(a) 誤統合の疑い: グループ内で条件を満たさないペア           0件
(b) 畳み損ね:     別グループの代表同士で条件を満たすペア      4件
      group 120(2件) と group 353(1件): T.N / 総武線 錦糸町駅 / 27歳
      group 197(2件) と group 371(2件): K.S / 田園都市線 鷺沼駅 / 58歳
      group 231(1件) と group 349(1件): R.N / JR東日本京浜東北線 浦和駅 / 26歳
      group 233(2件) と group 359(2件): T.T / 南海電鉄 帝塚山駅（大阪府） / 56歳
```

移植ロジックで1パス再計算すると435グループになり、実DBの439との差はこの4組と一致する。
**判定条件の差ではなく実行経路の差**である（取込時の `assignGroup` で付与された分と、
`backfillGroups` が処理した分が混ざり、照合対象の代表が処理時点で異なったため）。

畳み損ねは決定#34/#35の「厳しめに倒す」方針では許容側の誤り（現状と同じ状態にしかならない）。
再バックフィルで解消できるが `group_id` の振り直しになるため、
`matchings.staff_candidate_group_id` との整合を確認してから行うこと。

### 畳まれなかったレコード

```
イニシャル欠落:        4件
最寄駅トークンが空:   25件
年齢NULL:              3件（年齢条件がスキップされ、イニシャル＋駅だけで判定される）
```

イニシャル・最寄駅の欠損は必ず単独グループになる（案件側とは逆に、欠損を「判定材料なし＝一致」に
倒さない）。年齢NULLは現状3件と少ないが、**ここが増えると同一イニシャル・同一駅の別人を
分離する材料が無くなる**ため、抽出品質の監視対象とすること。

### 後日追記: 畳み損ねの解消（2026-08-20 16:40）

上記の畳み損ね4組を統合した（タスクH9）。あわせて `matchings` の候補行に
`staff_candidate_group_id` を補充した（タスクH8）。実行時点で取り込みが進んでおり母数は増えていた。

```
実行前 1,284件 → 502グループ / 誤統合0 / 畳み損ね4組
実行後 1,284件 → 498グループ / 誤統合0 / 畳み損ね0 / matchings不整合0
```

**`group_id` の全体振り直しはしていない**。振り直すと `matchings.staff_candidate_group_id` の
参照先がずれるため、存続させる側を「先に作られた＝`group_id` が小さい方」に寄せる形で
4組だけを統合した（統合方向は「存続側の最古レコードが victim 側より古いこと」を実行時に検証している）。

本レポート本文の数値（1,047件→439グループ）は 16:00 時点のスナップショットである。
以後の定点観測は `2way_ddl_local/ses_grouping_check.py`（リポジトリ外）で行う。

## Source

- 出所: `ses` スキーマ（`dev.2-way.co.jp:3306`）を pymysql + `ssl_disabled=True` で直接読み取り
- 取得日時: 2026-08-20 16:00 JST。`staff_candidates` 1,047件 + `mails` の受信日時を結合
- 判定ロジックの再現: `StaffCandidateGroupKeyResolver`（イニシャル正規化はNFKC＋トリム＋大文字化）と
  `LocationDictionary.tokenize`（括弧内除去→※以降除去→区切り分割→接尾辞除去→路線名接頭辞除去→8文字超破棄）
- 信頼度: 高（実データ全件。誤統合・畳み損ねは全ペア／全代表ペアの機械検査）
- 有効期限: **要再検証**。取り込み対象アカウントや送信元の顔ぶれが変わった場合、
  および要員情報の抽出ロジック（LLM）を変更した場合は再評価すること。
  特に `age` と `nearest_station` の抽出品質は判定に直結する
