# マッチングロジック: 実ユーザープロトタイプとの突き合わせ

確認日: 2026-08-17／確認対象: [SES Auto Send 企業テスト（実ユーザー作成プロトタイプ）](https://oso18-max.github.io/ses-match-pilot/prototype/company-test.html)

現行実装（[実装現状の記録](../development/implementation-status.md)）のマッチングロジックと、実ユーザーが持つイメージ（プロトタイプ）を突き合わせた記録。方向性の確認と、未決事項の洗い出しを目的とする。

## 1. プロトタイプの実像

- **総合点1軸（0-100点・順位付き）＋バンド運用**: 80点以上=提案候補／60〜79=要確認（単価・勤務地・スキル不足を見て営業判断）／59以下=見送り候補
- 点数の下に**条件別の内訳テーブル**（各行OK/NG＋理由の実値表示）:
  - 必須スキル一致／尚可スキル一致／不足スキル
  - 単価（例: 68万 <= 上限70万）／勤務地・リモート
  - **年齢制限**（例: 42歳 / 上限45歳）／**商流制限**（例: 二次請 / 上限二次請）／**NGワード**
- 除外理由サマリー（件数付き）
- **提案メール雛形の自動生成**＋送信先企業CSV（送信可否管理）
- 入力はフリーテキスト貼り付け→自動読み取り（読み取り結果の確認表示あり）
- 起点は案件→複数人材ランキング
- テストの合格ライン自体が「点数・除外理由・メール文面が**営業感覚とズレていないか**」

## 2. 合致している点（現行方針と骨格が一致）

| 観点 | プロトタイプ | 現行 |
|---|---|---|
| システムの役割 | 点数は営業感覚との答え合わせ。判定は人間 | 承認・見送りは人間操作、一覧は閲覧専用（[意思決定#6](../development/decision-log.md)） |
| スコアの主材料 | スキル一致（必須＋尚可） | 必須スキル80%・尚可スキル20%のスキル評価へ変更する |
| 待遇の扱い | 点数に混ぜず**条件別判定＋理由表示**（単価・稼働形態・開始時期・年齢・商流はOK/WARNING/NG、外国籍・個人事業主はOK/NG。決定#25） | NGありは対象外、NGなしはWARNING件数から条件係数を算出する |
| 根拠提示 | 判定理由・除外理由の明示 | matched/missing skills（拡張余地あり） |
| 表示形式 | 総合点1軸＋内訳テーブル | スコア0-100点表示（内訳表示は未実装） |

**設計上の含意**: 「要員は待遇を見る・案件はスキルを見る」という非対称性への実ユーザーの答えは、「待遇は点数に直接加点せず、条件別の判定理由として個別に見せる」。総合点は `skillScore * conditionFactor` とし、`NG` が1件でもあれば対象外、`NG` がない場合は `WARNING` 件数で条件係数を決める。画面には**内訳テーブル（条件別OK/WARNING/NGまたはOK/NG＋一致/不足スキル）を添える**。

## 3. ギャップ（現行モデルに無い要素）

1. **判定軸の不足**: 外国籍可否・年齢制限・商流制限・NGワードはデータモデルに概念が存在しない
   - 外国籍可否: 案件側の外国籍条件と要員側の国籍情報を比較する
   - 年齢: 要員側は `personnel.birth_date`（導出可）。案件側の上限年齢カラムが必要
   - 商流: 案件側の商流上限・要員側の商流位置ともに新規概念
   - NGワード: 保持場所・判定対象（案件文面か要員か）から要定義
2. **尚可スキルの加点**: 必須スキル一致率を80%、尚可スキル一致率を20%としてスキル評価を算出する
3. **スコープの先（Auto Send）**: 提案メール雛形の自動生成＋送信先企業CSV×送信可否管理まで想定されている。現行の提案管理（proposals）の一歩先のワークフロー

## 4. 未決事項の判断（2026-08-17 決定）

| # | 論点 | 決定 |
|---|------|------|
| 1x | 場所 | **初期版では自動判定しない**。案件側の場所と要員側の希望エリアを表示し、営業担当が判断する |
| 1y | 外国籍可否 | **追加する**。案件の外国籍条件と要員の外国籍情報をOK/NGで判定する |
| 1a | 年齢制限 | **追加する**。案件メールに記載があれば案件側に上限年齢を保持（取込時に抽出。記載なし=制限なし扱い） |
| 1b | 商流 | **AI抽出方針を暫定採用**。要員側は `personnelType` から導出（社員=自社直/BP=1社先）でAI不要。AI抽出が必要なのは案件側の商流上限のみで、既存のLLM取込抽出に項目追加（取込時1回・都度コストなし）。**検証済み実メール320通データセットで抽出精度を検証してから確定**。商流表現の正規化ルール（エンド直/元請/一次/二次→深さへの写像）を先に定義する。記載なし・曖昧は「不明」扱いで足切りしない |
| 1c | NGワード | **採用しない**（2026-08-18決定。保持場所・判定対象の定義が必要になった時点で再検討） |
| 1d | 総合点 | **追加する**。NGありは対象外。NGなしはWARNING件数から条件係数を決め、`score = skillScore * conditionFactor` とする |
| 1e | 境界値・7軸化 | **2026-08-18 決定#25**。単価乖離5万円以内/開始遅れ1ヶ月以内/年齢超過5歳以内はWARNING・超えたらNG。稼働形態は対応表で判定。商流はOK/WARNING/NGの3値（own_plus_support×BP=WARNING。上流同意済み）。個人事業主を7軸目（OK/NG）に追加。null軸はOK＋理由「判定材料なし」。詳細は[API契約](phase1-api-contract.md)マッチング節が正 |
| 2 | メール送信スコープ | **雛形生成まで**。送信は必ず人間が内容確認してから手動で行う（自動送信は過剰と判断しスコープ外） |

## 4.5 スキル経験年数の扱い（2026-08-18）

| 論点 | 状態 |
|------|------|
| 一致スキルへの**経験年数の併記**（表示のみ・判定に使わない） | **採用・実装**（決定#22-A）。候補・適合案件・マッチング一覧の一致スキルに要員の経験年数を添えて、人間の判断材料にする |
| 経験年数を**判定（フィルタ/スコア）に使う**か | **精度検証済み・採否は相談中**。案件側の要求年数（「Java 5年以上」等）は原文にしか無く構造化されていないため、商流と同方式で実メール171通の事前検証を実施（2026-08-18）: 捏造0・実質取りこぼし0・正規化一貫で**抽出は実用水準**（[精度検証](skill-years-extraction-verification.md)）。「目安」「程度」表現が多くハード足切りは実態より厳しくなるため、採用するならOK/NG＋理由表示（または減点）が適合。採否・方式は相談のうえ決定 |
