## 1. 決定事項（前提）

- マッチングは**直接一致のみ**。関連スキル展開（スコア部分点B・母集団拡大C）は廃案。
  skill_relationsはChipサジェスト（Y2）と結果画面の表示ヒント（Y3-A）専用
- 計算は**メール取込時の差分バッチ**へ移行。一覧表示時のオンデマンド全ペア評価をやめる
- 鮮度窓は**受信から1ヶ月**。設定値化して運用実測で調整可能にする
- スコア計算ロジック（MatchScoreCalculator・desiredSkillBonus含む）は**無変更**。
  変えるのは「いつ・どの母集団に対して計算するか」と「結果の持ち方」のみ

## 2. データモデル

### 2.1 matching_results（新設・計算結果の唯一のオーナー=マッチング計算段）

| 列 | 型 | 備考 |
|---|---|---|
| matching_result_id | BIGINT PK AUTO_INCREMENT | |
| project_id | INT NOT NULL | FK projects |
| counterpart_type | TINYINT NOT NULL | 0=personnel / 1=staff_candidate |
| counterpart_id | INT NOT NULL | |
| score | DECIMAL(5,2) NOT NULL | 評価時点の総合スコア |
| skill_score | DECIMAL(5,2) NOT NULL | |
| computed_at | DATETIME NOT NULL | |
| UNIQUE (project_id, counterpart_type, counterpart_id) | | 再計算はUPSERT |
| KEY (counterpart_type, counterpart_id, score) | | 要員視点の読み出し用 |
| KEY (project_id, score) | | 案件視点の読み出し用 |

- **保持対象**: 前置フィルタ（直接一致1件以上）通過かつ score > 0 のペアのうち、
  案件視点top-N **または** 相手視点top-Nに入るもの（Nは設定値・初期20）。
  規模見込み: 案件9,600×20 + 候補7,100×20 ≒ 30万行前後（重複はUNIQUEで畳まれる）
- スキル対比の明細（skillComparison）は保存**しない**。結果詳細画面は従来どおり
  ペア単位のオンデマンド計算（既存 `MatchingService.result()`。1ペアなので軽い）を維持する
- 提案スナップショット（proposals.match_snapshot）は従来どおり別物・無変更

### 2.2 鮮度窓の適用位置

鮮度（受信から1ヶ月・開始時期が過去でない）は**読み出し時のWHEREで適用**する。
行の寿命管理を再計算に依存させないためで、案件が窓から外れると自動的に一覧から消える。
古い行は日次パージ（受信からNヶ月超の案件の行をDELETE）で掃除する。

## 3. 計算フロー

### 3.1 取込時差分計算（本命経路）

メール取込runの構造化抽出完了後に「マッチング計算段」を追加:

1. run内で新規登録された projects / staff_candidates のIDを収集
2. 新規案件 × 窓内の全相手（personnel+staff_candidate）、新規候補 × 窓内の全案件を
   既存の前置フィルタ（直接一致）で絞り、通過ペアのみ評価
3. 結果をUPSERT。その後、影響を受けた視点のtop-N圏外の行を刈り取る（DELETE）

性能見込み（実測ベース試算）: 差分~450万ペア/日→フィルタ通過~140万評価/日→純Java計算で
数十秒オーダー。取込run本体（LLM 71分/1,103通実績）に対して誤差。
runの進捗・失敗はメール取込runの既存run管理に段として相乗りする（G1の宙吊りクローズも同じ機構に乗る）。

### 3.2 局所再計算（更新トリガ）

| トリガ | 再計算範囲 | 規模 |
|---|---|---|
| 要員/候補のスキル・希望スキル変更 | 当該1人 × 窓内全案件 | ~1万ペア・瞬時 |
| 案件の編集（スキル・開始時期等） | 当該1案件 × 全相手 | ~7千ペア・瞬時 |
| 手動登録案件の作成 | 同上 | 保存処理内で同期実行してよい規模 |
| 候補の昇格・非表示化 | 当該counterpartの行DELETE（昇格先personnelは上の行で再計算） | |

skill_relationsの承認/却下はスコアに影響しない（直接一致のみ）ため再計算不要。
Y3-Aのヒントは結果詳細画面のオンデマンド計算内で毎回引くので鮮度問題もない。

### 3.3 移行・初期投入

リリース時に一度だけ「窓内全件の初期計算」を実行する（管理APIまたは起動時ワンショット。
窓内が現devDB規模なら数分・本番想定9,600件でも差分と同じ経路を全件に適用するだけ）。

## 4. 読み出し（API・画面）

- マッチング一覧・案件候補一覧・要員適合案件: **matching_resultsを読むだけ**に変更
  （鮮度WHERE+score降順+ページング。既存のレスポンス形は維持し画面改修を不要にする）
- 同スコアの整列は**受信日時降順**を第2キーにする（鮮度の見える化）。
  一覧に受信からの経過日数の表示を追加する（Lavender側・小改修）
- 結果詳細（スキル対比+Y3-Aヒント）: 従来どおりオンデマンド1ペア計算。変更なし
- **MatchingListCacheは廃止**する。読みがインデックス付きテーブル参照になるためキャッシュ不要。
  無効化トリガ網（今回(e)で直した層）ごと消えるので、無効化漏れバグの類が構造的に再発しない
