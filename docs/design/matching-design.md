# マッチング・提案管理 設計（v0 ドラフト）

作成: 2026-08-07 / ステータス: **人間レビュー待ち**
関連: `mvp-requirements.md`（仮マッチング）、`data-model.md`、`skill-sheet-requirements.md`

---

## 0. 位置づけと方針

- MVP要件の「仮マッチング（単純文字列比較・余力時のみ）」を、**段階的にLLM推薦へ差し替え可能な構造**で設計する
- 方針: **単純なキーワード一致で終わらせない**。「Java⊇Java」の集合演算ではなく、
  隣接スキル・役割・フェーズ・ドメインを加味した**理由つき推薦**を目指す
- ただし説明可能性を捨てない: 足切りとタグ粗マッチは決定的なロジック、意味理解はLLMに分離

## 1. マッチングパイプライン（3段構成）

```
案件 ──┬─ ①ハードフィルタ(SQL) ──┬─ ②スキルタグ粗マッチ ──┬─ ③LLM推薦
       │  稼働時期・単価など        │  マスタ経由の集合演算     │  理由・ギャップ・提案文
       │  で明確な足切りのみ        │  上位N(=20)に絞る         │  1案件1回の呼び出し
```

| 段 | 実装 | 役割 | 説明可能性 |
|----|------|------|-----------|
| ① | SQL/ルール | 単価、稼働形態、稼働開始時期、外国籍可否、年齢、商流を条件別に判定 | 完全 |
| ② | スキルマスタのタグ集合演算 | 必須スキル80%・尚可スキル20%のスキル評価で候補を上位N件に圧縮 | 完全 |
| ③ | LLM（gpt-5.6-luna 流用） | 隣接スキル推論・適合度・理由・ギャップ・提案文ドラフト | 出力に理由を含めることで担保 |

- 場所は初期版では自動判定しない。案件側の場所と要員側の希望エリアを表示し、営業担当が判断する
- 条件適合は項目ごとに `OK` / `WARNING` / `NG`、または `OK` / `NG` と判定し、理由を保持する
  - `price` / `workStyle` / `startDate` / `age`: `OK` / `WARNING` / `NG`
  - `nationality` / `commercialFlow`: `OK` / `NG`
- `NG` が1件でも含まれる場合はマッチング対象外とする
- `NG` がない場合、`WARNING` 件数で条件係数を決め、`score = skillScore * conditionFactor` で総合点を算出する
  - `WARNING` 0件: 1.00
  - `WARNING` 1件: 0.90
  - `WARNING` 2件: 0.80
  - `WARNING` 3件以上: 0.70

### 稼働開始時期の動的判定（2026-08-27）

`startDate` は保存済み年月だけを固定比較せず、マッチング計算時点の当月を基準に毎回判定する。
要員メールに稼働ステータスは追加せず、既存の開始可能月と開始時期原文から待機相当かを導出する。

- 要員の開始可能月がまだ先の場合
  - 要員開始月と案件開始月が同月: `OK`
  - 案件開始が要員開始月より後: `WARNING`（希望より遅い）
  - 案件開始が要員開始月より前: `NG`（開始に間に合わない）
- 要員の開始可能月が計算月に到来済みの場合は待機相当とみなす
  - 当月・翌月開始の案件: `OK`
  - 翌々月以降の案件: `WARNING`
- 要員側の「即日」は計算月を開始可能月として扱う
  - 当月・翌月開始の案件: `OK`
  - 翌々月以降の案件: `WARNING`
- 案件側の「即日」も計算月を開始月として扱う
  - 要員の開始可能月が当月以前または翌月: `OK`
  - 要員の開始可能月が翌々月以降: `WARNING`
- 「即日」は `start_text` の原文で判定する。ステータスや新しいLLM抽出項目は追加しない
- 一覧評価は既存の10分キャッシュを使用するため、月替わりの反映は最大約10分遅れることがある

- ③はメール抽出で実績のある **luna × 最小プロンプト** をそのまま流用（ヒューリスティックを盛らない）
- ③の出力（構造化）: `fit_score`(高/中/低), `reasons[]`, `gaps[]`（あと何があれば立てるか）, `concerns[]`, `proposal_draft`
- **ニアミス候補も返す**: 完全一致だけでなく「ギャップ1つの惜しい候補」を明示 → 育成/BP調達の判断材料

### コスト目安

1案件×候補20名の要約を1回の呼び出しに同梱。メール分類実績（320通で$1未満）から、
日次の新規案件数十件に対して**月額数ドル〜十数ドル**の見込み。詳細は実装前に試算。

## 2. スキルマスタ（運用負担を最小化する構成）

| テーブル | 役割 |
|----------|------|
| `skills` | 正規スキル（id, canonical_name, category）。**数百語で開始**（3,000語は不要） |
| `skill_aliases` | 表記ゆれ吸収（JAVA/java8/Java SE → Java）。マスタ本体と分離 |
| `unknown_terms` | マスタ未登録語のプール（term, freq, first_seen, status）。頻度閾値超えで登録候補化 |

- **初期シード**: 検証済み320通の抽出スキル頻度から自動生成（手作業でゼロから作らない）
- **運用**: LLMが「既存○○の別表記では？」と正規化提案 → 人間承認のみ。自動登録はしない
- マスタが不完全でも②が粗くなるだけで③が救う（マッチング品質がマスタ精度に一蓮托生にならない）
- スキル隣接グラフは**持たない**（まずLLM推論で代替。パターンが見えたら構造化を再検討）

## 3. 暗黙要件の構造化（抽出スキーマ拡張）

現行luna抽出（title, required/preferred_skills_text, price, location, remote_type, start, interview_count）に追加:

| フィールド | 値域案 | 狙い |
|-----------|--------|------|
| `role` | member / lead / architect / pm | 「Java 5年」同士でも設計リードと保守実装を区別 |
| `phases[]` | 要件定義〜保守 | 上流経験の要否 |
| `domain` | 金融/EC/物流/公共/... | 業務知識のマッチ |

スキルシート側（ブラウザ入力）にも同じ3軸のタグを持たせる。**案件と人材が同じ語彙で記述される**ことが②③の精度の土台。

## 4. 提案管理（★物理側要件の反映）

> **注**: 会社側（物理）の要件に「提案管理」があるが、現行 `mvp-requirements.md` は
> 「営業管理全般」をスコープ外としており**乖離がある**。スコープ確定は人間の判断待ち（§6）。

マッチングは「候補を出して終わり」ではなく提案ライフサイクルに接続する:

```
候補者リスト → 提案作成(draft) → 提出(submitted) → 面談(interview) → 成約(won) / 見送り(lost)
```

### `proposals` テーブル案

| カラム | 内容 |
|--------|------|
| id, project_id | 対象案件（`projects` FK相当。スキーマまたぎJOIN禁止の制約に従いFKは張らない） |
| engineer_id / staff_id | 自社エンジニア or BP要員（どちらか一方） |
| status | draft / submitted / interview / won / lost / withdrawn |
| proposal_text | 提案文（③のドラフトを人間が編集した最終版） |
| match_snapshot | 提案時点の③出力（score/reasons/gaps）をJSONで凍結保存 |
| sent_at, interview_at, result_at, lost_reason, memo | 経緯記録（面談予定日時を含む） |

- `match_snapshot` が**フィードバックループの布石**: 「どんな推薦が通ったか」が自動で溜まる。
  機械学習はスコープ外のまま（要件通り）、**スキーマだけ先に切っておく**
- 画面フロー: 案件詳細 → 候補者リスト（③の理由つき）→ ワンクリックで提案作成 → 提案一覧でステータス管理

## 5. 画面・ルーティング（要員統合IA / 2026-08-07 人間発案）

### 考え方

社員もBPも広義では「要員」であり、スキルシートを持つ点も同じ。
**「スキルシート」をトップメニューにするのではなく「要員」を軸にし、
スキルシート・マッチング・提案状況を要員詳細の配下に置く。**

### 要員の3種を区別する（重要）

| 種別 | 実体 | 管理方法 |
|------|------|----------|
| 社員 | 自社エンジニア | `personnel`（type=employee）。スキルシートは正本管理 |
| 管理BP | 継続取引のあるパートナー要員 | `personnel`（type=bp）。同じ画面・同じシート構造 |
| メール抽出staff | 他社からの売り込み（日数百通から抽出） | **`personnel`に入れない**。`staffs`（リード）のまま別置き |

メール抽出staffを要員一覧に混ぜると、精査済みの一覧が自動抽出の大量データで汚れる。
`staffs` はあくまで候補プールとし、実際に取引が始まった時点で **「要員として登録」する昇格フロー**
（staffs → personnel へのコピー登録）で接続する。

### ルーティング案

```
/ses/personnel                要員一覧（社員/BPフィルタチップ）
/ses/personnel/:id            要員詳細 — タブ構成:
                                基本情報 / スキルシート / 適合案件(マッチング) / 提案状況
/ses/projects                 案件一覧
/ses/projects/:id             案件詳細 — タブ構成:
                                案件情報 / 候補要員(マッチング) / 提案状況
/ses/proposals                提案一覧（横断ビュー・ステータス管理）
```

- マッチングは**双方向の同じバックエンド**を2つの入口から見せる:
  要員詳細「適合案件」（この人に合う案件）／案件詳細「候補要員」（この案件に合う人）
- 提案も同様に、要員起点・案件起点・横断一覧の3ビューで同じ `proposals` を見せる
- サイドバー「SES」配下は **「要員」「案件」「提案」** の3項目に整理
  （`lavender-integration.md` の現行案「スキルシート」「案件一覧」から変更 → 要更新）

## 6. 段階導入

**2026-08-07 人間判断: 実装対象は Phase 1。③LLM推薦は後回し**
（都度コストが発生する機能を先に実装しない。①②とproposalsはランニングコストゼロで完結する）。

| Phase | 内容 | 備考 |
|-------|------|------|
| **1（実装対象）** | ①②＋`proposals`（手動ステータス管理） | MVP「仮マッチング」の置き換え。LLM不使用・ランニングコストゼロ |
| 2（保留） | ③LLM推薦＋提案文ドラフト＋暗黙要件3軸 | 抽出スキーマ拡張を含む。Phase1の運用実績を見て判断 |
| 3（保留） | match_snapshot活用（提案結果の振り返り分析） | 機械学習はやらない。集計・可視化まで |

Phase 1 でも設計は③を前提に置いておく（候補者リストのAPI応答に理由フィールドの席だけ
確保する等）。後から③を差し込むときに画面・スキーマの改修が起きない形にする。
