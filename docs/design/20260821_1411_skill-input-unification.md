# スキル入力の一本化設計 — スキルシート正・基本情報は派生（案X）

決定ログ採番は実装セッションで行う。

## 1. 目的と決定事項

メンバーのスキル入力が実質3箇所（基本情報の保有スキル `personnel_skills`／スキルシートの
スキル一覧 `skill_sheet_skills`／経歴の使用技術 `skill_sheet_careers.technology`）にあり
二重・三重入力になっている。**人間決定（2026-08-21）: 案X＝スキルはスキルシートにだけ書き、
マスタ紐付け（`personnel_skills`）はシート記載から半自動生成。
基本タブのスキル欄は削除する（編集はスキルシート・表示はスキルシートタブ。
「調整画面に格下げ」案は不採用＝同日追加決定）。**

## 2. 現状の事実（2026-08-21 調査。ファイル:行は当時点）

- `personnel_skills`（skill_id・years、UNIQUE(personnel_id, skill_id)）の書き込み経路は2つ:
  1. `PersonnelService.regist()`（PersonnelService.java:265-279）— メンバー編集の保存で**全削除→洗い替え**
  2. `StaffCandidateService.promote()`（StaffCandidateService.java:303, 413-434）— 昇格時に
     `staff_candidate_skills` をグループ横断で重複除去してコピー（**years=NULL**）
- `skill_sheet_skills` は name（varchar64・自由入力）・category（フロント固定enum）・
  experience_months を持ち、**マスタ（skill_id）と一切紐付かない**（2026-08-05決定のコメントあり）。
  書き込みは `SkillSheetService.replaceSkills()`（洗い替え）
- マッチングのスキル軸（skillScore・skillYears）が読むのは **`personnel_skills` のみ**。
  `skill_sheet_id` の有無は見ない＝シート未作成でもタグがあればマッチングに乗る
- マスタは `skills`（canonical_name UNIQUE）＋ `skill_aliases`（alias_text UNIQUE）。
  照合は `SkillTextMatcher`（NFKC＋小文字化、ASCII語は語境界判定、`similarityRank()` で
  完全一致0/包含1/編集距離2+）。未知語は取込バッチが `unknown_terms` に蓄積し、
  `unknownTermTriage.tsx` → `decision` API（新規登録/別名登録/却下→該当語だけ再照合）で人間確定。
  **この機構は projects / staff_candidates 専用で personnel には未接続**
- dev実測（2026-08-21）: personnel 14名（シート未作成3名）・personnel_skills 保有12名・
  skill_sheet_skills 54行
- 前提タスク: **W1（シートのスキル名を freeSolo Autocomplete でマスタサジェスト化）が先行**。
  表記が揃うほど本設計の自動対応付け精度が上がる

## 3. 設計方針

### 3.1 データフロー（一本化後）

```
スキルシート編集（入力はここだけ）
  └ 保存 → SkillSheetService.edit()
      ├ replaceSkills() … skill_sheet_skills 洗い替え（従来どおり・原文尊重）
      └ ★syncPersonnelSkills() … シート記載→personnel_skills の同期（新設・同一トランザクション）
          ├ 完全一致＋決定的展開（→3.4）で対応付いた語 → 自動でタグ生成
          ├ 非一致 → タグ化しない（原文はシートに残る＝マッチング対象外）
          └ years = experience_months ÷ 12（切り捨て）

メンバー詳細・編集（基本タブ）
  └ スキル欄は削除（表示・編集とも持たない。表示はスキルシートタブに一本化）

personnel_skills はシートが唯一の入力源になる:
  ├ シートあり: 保存のたびにシート由来で全洗い替え
  └ シートなし: 昇格コピー分のタグがそのまま残る（初回シート保存で置き換わる）
```

### 3.2 論点ごとの設計判断（提案）

| # | 論点 | 提案 | 理由 |
|---|------|------|------|
| 1 | 導出方法 | NFKC＋小文字化の完全一致に**決定的展開（3.4）を加えて自動確定**。編集距離による曖昧対応はしない（**2026-08-21人間決定**） | 実測: 完全一致のみ55%→決定的展開込み85%。展開は決定的な文字列変換のみで誤統合は構造上起きない。決定#30/#35の教訓とも整合 |
| 2 | 非一致語の扱い | 方針B踏襲＝原文のままシートに残す（マッチング非対象）。当座は**移行時にマスタ語彙を一括整備**して非一致を解消（実測の残7語: centos / django / sqlite / react.js / oracle database / ubuntu server 等はマスタ追加・別名登録で対応可）。可視化と `unknown_terms` 蓄積は**フェーズ2**（**2026-08-21人間決定**） | マスタ強制しない方針を維持しつつ実データの非一致を移行時に潰す。蓄積の書き込みオーナー原則（取込バッチのみ）も当面崩さない |
| 3 | 経験年数 | `experience_months ÷ 12` 切り捨て。**手調整UIは持たない**（導出のみ。直したければシートの経験月数を直す。**2026-08-21人間決定**） | 切り捨ては skillYears 軸でWARNINGが出やすい方向＝営業が確認する側に倒れる安全側。入力源を1つに保つ |
| 4 | 同期タイミング | **シート保存時に自動同期（完全一致分のみ）**。確定ダイアログは挟まない | 自動確定の範囲を完全一致に絞ることで確定ステップの安全性を担保しつつ、入力の痛み軽減という目的を損なわない。非一致語はそもそもタグ化しないので誤統合リスクがない |
| 5 | 既存データ移行 | シート保有者は**初回同期で全洗い替え**（シート記載が正）。移行スクリプトはドライランで「消えるタグ・増えるタグ」の差分を人間提示してから本実行（**2026-08-21人間決定**）。移行と同時に非一致語のマスタ整備（下記2）を行う | 「シートが正」の決定に忠実。差分提示で気付けない劣化を防ぐ |
| 6 | 基本タブのスキル欄 | **削除**（表示・編集とも）。表示はスキルシートタブ、編集はスキルシート編集に一本化（2026-08-21 人間決定） | 同じデータを2画面で見せる必要はない。`fetchSkillSuggestions` 等の関連stateも撤去 |
| 7 | シート未作成メンバー | 従来どおりマッチングに乗る（昇格コピー分の `personnel_skills` が残るため）。新規タグ追加の窓口は無くなるので、スキルを持たせたければシートを作る運用。**基本タブに「スキルはスキルシートで管理」の案内＋作成導線**を出す | 3名が該当。シート作成が実質の入力窓口になるが、強制はしない |

### 3.3 同期の詳細仕様

- 同期は `SkillSheetService.edit()` 内、`replaceSkills()` 直後に新設メソッドで実施（同一トランザクション）
- 内容: シートに紐付くメンバー（`personnel.skill_sheet_id`）の `personnel_skills` を**全削除→
  シート記載の完全一致分で再生成**（years は導出値）。手調整・sourceカラム・マージは**持たない**
  （基本タブのスキル欄削除の決定により、シート保存が唯一の書き込み契機になるため区別が不要）
- **スキル行が0件のシートは同期しない**（既存タグ維持。2026-08-21人間決定。実測でシート保有12名中
  3名がスキル欄未記入であり、全洗い替えだとタグ全損→マッチングから突然消えて人間が気付けないため。
  「未記入=未入力」とみなす。タグをゼロにする操作はこの仕様では表現できない点は既知の制約）
- 昇格コピー（`StaffCandidateService.promote()`）は現状維持。シート未紐付けメンバーの
  タグとして残り、初回シート保存時に置き換わる
- `PersonnelService.regist()` から skills 洗い替え処理を**撤去**し、`PersonnelInput.skills` を
  API契約からも落とす（フロントの送信も削除。契約更新が必要）
- 同期はメンバー紐付け済みシートのみ対象。未紐付けシートは保存時に何もしない
  （紐付け時（linkToMember）にも1回同期を走らせる）

### 3.4 決定的展開の仕様（対応付け前の文字列変換。2026-08-21実測済み）

1. NFKC正規化＋trim＋小文字化（`SkillTextMatcher.normalize()` と同一）
2. 括弧注記の除去: `（）` `()` 内を落とす（例: `jenkins (パイプライン設計含む)` → `jenkins`）
3. 区切り分解: `/`・`・`・`,` で分割し、各断片を独立に対応付け（例: `docker / docker compose` →
   `docker` と `docker compose` の2タグ。UNIQUE制約があるので重複はスキップ）
4. 末尾バージョンの反復除去: `\s+(v?数字[数字.]*[a-z]?)( lts)?$` を繰り返し剥がす
   （例: `java 17` → `java`、`ubuntu server 22.04 lts` → `ubuntu server`）。
   素の形で一致すればそちらを優先し、剥がした形は一致しなかった場合のフォールバック
- dev実測（2026-08-21・53行）: 素の完全一致 29行(55%) → 展開込み 45行(85%)。
  残8行はマスタ語彙の欠落（centos等）で、移行時のマスタ整備で解消する

## 5. 影響範囲・非対象

- マッチングの読み取り経路（`personnel_skills` 直読み）は**変更しない**。挙動変化は
  「タグの入り方」だけで、判定ロジック・スコア計算は不変
- スキルシートの表示・印刷・`skill_sheet_skills` の持ち方は不変（原文尊重）
- 経歴の使用技術（`skill_sheet_careers.technology`）は今回対象外（自由テキスト1本のため
  対応付け精度が見込めない。スキル一覧への転記を促す運用で吸収）
- 要員候補（staff_candidates）系の未知語フロー・昇格コピーは不変
