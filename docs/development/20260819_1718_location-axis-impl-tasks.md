## 0. なぜ手順5と同時なのか

手順5は `MatchSubjectData.of(Personnel, ...)` を `personnel` 直読みへ切り替える工程。
location軸が要員側の判定材料（`prefecture` / `preferredLocation` / `nearestStation`）を取るのも同じ場所。
**別々に進めると同一ファイルを2度触ることになる**ため、手順5の中に取り込む。

対象ブランチ: thyme `feature/skill-sheet`（未コミット差分が30ファイル超あるので、着手前に現状を確認すること）

## 2. 判定ロジック（そのまま実装できる形）

```
location(案件location文字列, 案件remoteType, 案件region, 要員region) -> OK / WARNING / NG

1. 案件locationに否定キーワードを含む
     → 地方一致必須。region両方が非nullで不一致なら NG、一致なら OK、どちらかnullなら OK＋「判定材料なし」
2. remoteType == 0（フルリモート）
     → OK 理由「案件はフルリモート」
3. remoteType == 1（併用）かつ 案件locationに低頻度出社キーワードを含む
     → 両方非nullで不一致なら WARNING、それ以外は OK
4. 案件region == null または 要員region == null
     → OK ＋ 理由「判定材料なし」（どちら側が欠けているかで既存の NO_MATERIAL_* を出し分ける）
5. 一致 → OK 理由「案件は関東 / 要員は関東」のように実値を入れる
6. 不一致 → NG 理由「案件は関東 / 要員は関西」
```

既存8軸と同じ `check(STATUS_X, reason)` / `noMaterial(projectMissing, personnelMissing)` を使う。
理由文には必ず実値を入れる（既存軸の作法に合わせる）。

### 落とし穴

**`MatchScoreCalculator.countStatus` の集計配列に `location` を足し忘れると、軸を追加しても
NG判定もWARNINGカウントも効かない。** 現状は8要素の配列にベタ書きされている（756行付近）。
テストで必ずここを踏むこと（§6のケース7）。

## 3. 辞書引きの実装（重要）

### 3.1 部分一致は禁止。トークン完全一致で引く

実データに次の衝突がある。部分一致だと全部誤判定する。

| 誤って一致するもの | 正しい扱い |
|---|---|
| `岩本町`（東京） に `本町`（大阪）が部分一致 | 別トークンとして扱う |
| `東中野`（東京） に `中野`（東京） | 結果は同じだが原理的に危険 |
| `天王洲アイル` に `天王洲` | 別エントリで両方持つ |
| `大和田`（埼玉） に `大和`（神奈川） | 別トークンとして扱う |
| `山手線`（路線名） に `山手`（横浜の駅） | 路線名は前処理で落とす |

### 3.2 前処理の手順

1. 括弧内の注記を除去（`（）` `()` `【】` `[]`）
2. `※` 以降を除去
3. 区切り文字で分割: `、` `,` `／` `/` `・` 空白 `または` `もしくは` `or`
4. 各トークンの末尾から `駅` `近郊` `近辺` `沿線` `周辺` `社内` `エリア` `方面` を除去
5. 各トークンの先頭から路線名を除去: `JR` `京王線` `小田急線` `東京メトロ` `大阪メトロ` `阪急` `南海`
   `山手線` `日比谷線` `西武新宿線` `西武池袋線` `御堂筋線` `都営新宿線` `京急` `東急` `近鉄` `地下鉄`
6. 8文字を超えるトークンは捨てる（注記の残骸）
7. 残ったトークンを辞書に完全一致で引く

### 3.3 複数トークンが異なる地方に当たった場合

**いずれか1つが要員の地方と一致すればOK**とする（`六本木一丁目駅or金沢駅` のような案件のため）。
一致するものが1つもなければ不一致とする。

## 5. 曖昧地名の判断（要目視確認）

設計書§6は当初「同名地名は一律で辞書から除外」としていた。実データを引くと大半は一意に決まったため
本書では「根拠のあるものは倒す」案を提示したが、**2026-08-19の人間判断で当初方針どおり9語すべて除外することに決定した。**

**決定: 下表の9語はいずれも辞書に入れない。** 未知語は §2 の #4 に落ちて「判定材料なし＝OK」になるため誤除外は起きない。
実データ上は一意に決まる語もあるが、将来他地方の案件が入ったときに**誤NGは候補一覧から消えて人間が気付けない**のに対し、
誤OKは営業担当が弾ける。この非対称性を重く見て、安全側に倒した。

以下は判断の材料として残す（将来「やはり倒す」と決めるときの根拠）。

| 地名 | 頻度 | 実データの中身 | 判断 |
|---|---|---|---|
| `府中` | 60 | 全て東京都府中市（`府中駅 ※上位現場常駐` 等）。広島県府中市は0件 | 除外（当初案: 関東） |
| `本町` | 8 | `大阪・本町（検証）`『本町／テレワーク併用＋新大阪』→ 大阪 | 除外（当初案: 関西）。なお `岩本町`(東京)は辞書に残るため、部分一致禁止は引き続き必須 |
| `大手町` | 14 | 全て東京（`大手町（週1出社）` 等）。福岡市の大手町は0件 | 除外（当初案: 関東） |
| `淡路` | 5 | 候補側 `阪急 淡路駅` → 大阪。案件側の `淡路町` は東京で別トークン | 除外（当初案: 関西）。`淡路町`は関東で別登録のまま残す |
| `橋本` | 35 | `京王線 橋本駅` → 神奈川県相模原市。福岡・和歌山の橋本は0件 | 除外（当初案: 関東） |
| `大和` | 10 | `相鉄線・小田急線 大和駅` → 神奈川県大和市。奈良の大和は0件 | 除外（当初案: 関東）。`大和田`(埼玉)は別トークンとして残す |
| `三田` | 6 | `都営三田` `浜松町駅、大門駅、三田駅` → 東京都港区 | 除外（当初案: 関東） |
| `福島` | 6 | `大阪駅/福島駅` → 大阪市福島区。ただし福島県と完全に同名 | **除外**（判定材料なし） |
| `山手` | 5 | `山手駅（神奈川県）` と `山手線`（路線名）が混在 | **除外**。路線名の前処理漏れで誤トークン化しやすい |

**誤NGは候補一覧から消えて人間が気付けないが、誤OKは営業担当が弾ける。** 迷ったら除外側（＝判定材料なし＝OK）に倒す。

## 6. キーワード辞書

### 6.1 否定キーワード（最優先で判定）

```
地方不可	フルリモート限定は対象外	地方在住不可	首都圏在住	通勤圏
```

実在例:
- `基本リモート（参画時に豊洲出社あり／地方不可）`
- `基本テレワーク（チームMTG・顧客打合せ時に出社あり。フルリモート限定は対象外）`
- `フルリモート※地方不可`

**これを `remoteType == 0` の例外判定より後ろに置くと、上記が誤ってOKで通過する。**

### 6.2 低頻度出社キーワード（併用案件をWARNINGに緩める）

```
基本リモート	原則リモート	基本テレワーク	リモート主体	ほぼリモート	月1	月一
```

併用722件のうち該当は57件（7.9%）。残る92%は地方不一致ならNGになる。
