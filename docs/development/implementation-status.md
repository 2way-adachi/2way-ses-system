# 実装現状の記録（SES機能）

Lavender／thyme上のSES機能の現状を記録する。**要件ではなく、2026-08-26時点で確認した実装事実**を扱う。

- 作成日: 2026-08-17
- 更新日: 2026-08-26
- 確認対象: Lavender、thyme、最新画面モック

## 1. 現在の全体像

| 領域 | 現状 |
|------|------|
| ナビゲーション | SES大項目と6メニューを実装。権限定義で表示を制御 |
| 案件・要員メール | 取込バッチ、API、一覧、詳細編集、原文、実行状況・履歴を実装 |
| メンバー | 一覧、新規、編集、4タブ詳細を実装 |
| スキルシート | メンバー詳細タブへ統合。作成、編集、下書き、PDFを実装 |
| マッチング | 一覧、同一案件グループ、双方向結果、内訳、昇格、承認を実装 |
| 提案 | 一覧、カード、案件面談回数に応じた動的ステッパー、次ステップ／見送り更新フォームを実装 |
| スキルマスタ | 登録待ちスキルの仕分け、マスタ管理、マージ、再照合を実装 |

画面ルートの一覧は [画面設計](../design/screen-design.md) と
[Lavender組み込み要件](../requirements/lavender-integration.md) を参照する。

## 2. Lavender

### 2.1 メニューと権限

`src/index.tsx` には次の6メニューがある。

1. 案件メール一覧
2. 要員メール一覧
3. メンバー一覧
4. マッチング一覧
5. 提案管理一覧
6. スキルマスタ

メニューは許可された機能に絞って表示される。一般ユーザーを自分のメンバー詳細へ誘導する処理と、管理ユーザー管理画面も実装されている。

### 2.2 案件・要員メール

- `/project-mail`、`/project-mail/:id`
- `/staff-mail`、`/staff-mail/:id`
- API接続済みの一覧、検索、ページング、詳細編集
- メール原文カード
- 手動取り込み、実行中ポーリング、直近サマリ、履歴ダイアログ

旧モック用の `/project`、`/staff` は現在の正規導線ではない。

### 2.3 メンバーとスキルシート

- `/member`、`/member/new`、`/member/:id`、`/member/:id/edit`
- 詳細タブは `info`、`skill-sheet`、`matching`、`proposal` の順
- 登録・編集では基本属性、希望条件、スキルタグを扱う。既存スキルシートの選択・紐付け変更は編集時のみ
- スキルシート未作成時はメンバー詳細から新規作成し、保存時に紐付ける
- 既存シートは表示、編集、印刷用PDFへ遷移できる
- 編集画面は基本情報、経歴、スキル／資格の3タブ
- 経歴は「経験者」「未経験者」を選択して追加する
- スキル／資格タブでは、スキルマスタから「やりたい技術」を最大5件登録できる。詳細画面にも独立した項目として表示する

独立したスキルシート一覧・詳細は現在の画面構成では使用しない。

### 2.4 マッチング

- `/matching` に結果一覧を実装
- メンバーと要員候補を同じ一覧で扱い、同一案件の結果をまとめて表示
- 勤務地を判断材料として表示
- メンバー／候補者ごとの結果画面と、案件詳細への導線を実装
- 要員候補をメンバーへ昇格する操作を実装
- メンバー詳細で承認、見送り、差し戻し、提案作成を実装
- 総合点、スキル点、条件係数、条件別ステータス・理由を共通表示

候補者昇格と承認UIを削除する変更案（C8）は未適用。実装とモックには現在も残っている。

- **新スコア仕様（決定#25）を実装済み（2026-08-18。devDB実機検証済み）**。仕様の正は
  [phase1-api-contract.md](../design/phase1-api-contract.md) マッチング節
- experienceSkillScore = 必須スキル一致率×0.8＋尚可一致率×0.2（片側0件はもう片方100%扱い）。必須/尚可は
  project_skills.required で区別し、タグ付けは required_skills_text / preferred_skills_text の
  原文出現で区分（どちらにも出現しない語は必須扱い）。既存データは再照合APIで新区分に収束
- メンバー登録済み要員は、やりたい技術が案件の必須スキルに一致するごとに3点、尚可スキルに一致するごとに1点を加点する。
  同じ技術が必須・尚可の両方にある場合は必須のみとし、加点上限は10点。未経験の希望技術は経験上の一致や不足解消には使わない。
  `desiredSkillBonus = min(0.10, 必須一致数×0.03 + 尚可一致数×0.01)`、
  `skillScore = min(1.0, experienceSkillScore + desiredSkillBonus)`。メール要員と希望未登録メンバーは従来どおり
- conditionChecks 7軸（単価・稼働形態・開始時期・年齢・商流=OK/WARNING/NG、外国籍・個人事業主=OK/NG）、
  各軸に日本語の理由。単価は対の値が揃えば部分判定（上限のみ記載の案件でも判定）
- 開始時期は計算月に応じて動的判定（2026-08-27実装）。未来の開始可能月は同月案件=OK・後=WARNING・前=NG、
  開始可能月到来済み／要員即日は当月・翌月案件=OK、翌々月以降=WARNING。案件即日は要員が翌月開始までOK。
  要員メールに稼働ステータスやLLM抽出項目は追加せず、既存の`start_ym`・`start_text`から都度導出する
- NG1件で候補から除外。conditionFactor=1.00/0.90/0.80/0.70、score=skillScore×conditionFactor
  （小数第2位丸め・表示は0〜100点）。ソートはscore降順→一致数降順。
  案件→候補要員は上位20件のまま。要員→適合案件は上位20件固定を撤廃し全件対象+サーバーページング
  （status/unproposedOnly/projectTitle/scoreMin/page/size、レスポンスは{items,total}。
  各行にmailReceivedAt=元メール受信日時を追加。2026-08-25実装・未コミット）
- match_snapshotはversion付きv2で凍結（既存v1は無移行で従来表示）
- 実装メモ: 要員側の remote_preference・preferred_location は skill_sheets 側のカラムのため
  紐付きスキルシート経由で取得（未紐付けは「判定材料なし」でOK通過）
- フロントは総合点1軸＋内訳テーブル（skillScore×conditionFactor・条件別status/理由・場所参考行）を
  共通コンポーネント matchBreakdown で3画面＋提案控えに表示
- 双方向（案件→候補要員／要員→適合案件）、推薦理由はPhase2のLLM用の席のみ（従来どおり）
- **要員候補（未昇格BP）も評価対象**（決定#31。2026-08-20実装）: staff_candidate_skills でタグ付けし、
  候補側は単価・開始時期・年齢（直接値）・商流/個人事業主（affiliationから導出）で判定。
  稼働形態・外国籍・経験年数は判定材料なし。イニシャル名での自動昇格API（冪等・タグコピー・matchings付け替え）
- **location軸（9軸目）**（決定#34）: 8地方区分辞書で案件の勤務地と要員所在地を突き合わせ。
  否定キーワード最優先→フルリモート例外→低頻度出社はWARNING→特定不能は判定材料なし。`projects.region` に保持
- **同一案件グルーピング**（G1）: タイトル正規化＋勤務地トークン＋単価レンジで `projects.group_id` に付与。
  マッチング母集団は代表1件のみ、承認/見送りはグループ単位で引き継ぎ、結果画面はグループ内の全メールを提示
- **要員候補の名寄せ**（決定#35。2026-08-20実装）: イニシャル＋最寄駅トークン＋年齢で `staff_candidates.group_id`
  に付与。所属はキーに使わない（表記ゆれで割れるため）。マッチング母集団は代表のみ、昇格も代表からのみ可。
  実データ1,047件→439グループ・誤統合0件（[精度検証](../design/20260820_1616_staff-candidate-grouping-accuracy.md)）。
  イニシャルまたは最寄駅が空のレコードは畳まない
- **性能対策**（決定#31）: 共通スキル前置フィルタ・案件の鮮度フィルタ（開始時期が過去/受信1ヶ月超は評価対象外。
  ただし`start_text`が即日の案件は計算月開始として対象）・
  一覧のサーバ内キャッシュ。実測はマッチング一覧がコールド4.2秒・キャッシュ0.2秒（対策前は数分）
- **運用手順**: relink（全件再照合）は約5秒。ただし required_years が一部失われるため、
  **relink後は skill-years-backfill を続けて実行する**。region・group_id にもバックフィルAPIがある

### 2.5 提案

- `/proposal` に提案一覧を実装
- 一覧からメンバー詳細の提案状況タブへ遷移
- 提案1件をカード表示し、案件の想定面談回数ぶん「1回目面談済」から「N回目面談済」まで展開する動的ステッパーで進捗を可視化
- ステータス、面談日時／回数、次回アクション日、メモを更新
- ステータス値は提案準備中、提案メール送信済、面談済、結果、採用、見送り、取下げ、参画（採用は参画前の進行中）
- 最終面談後は「結果」を選択させず採用／見送りを直接選択する。確定後はステッパーの「結果」を選択文言へ置換し、採用時だけ参画を追加

### 2.6 スキルマスタ

- `/skill-master` に登録待ちスキルとマスタの画面を実装
- 登録、別名への紐付け、対象外、マージ、再照合を操作可能

## 3. thyme

### 3.1 営業メール取り込み

- IMAPS読み取り専用接続
- ヘッダ／本文の段階取得
- Message-IDによる重複排除
- ルール除外後、OpenAI Responses APIのStructured Outputsで案件／要員／その他を分類・抽出
- 複数案件・要員の分割登録
- `mails`、`projects`、`staff_candidates` とスキル照合結果を保存
- 手動実行API、設定可能なスケジューラ、プロセス内多重起動ガード
- 実行ヘッダとアカウント別明細による履歴管理

実IMAP、実OpenAI、開発DBを使った結合確認では、初回873通、LLM処理829通、案件536件、要員候補331件を登録し、2回目は新着のみを処理して重複登録がないことを確認している。

### 3.2 メンバー・スキルシート・提案

- `personnel` をメンバーの正本として拡張し、登録・参照・更新APIを実装
- スキルシートの一覧、詳細、保存、下書き取得／保存／削除APIを実装
- 提案の一覧、作成、更新APIを実装
- `interview_done_count` と `next_action_date` を保持
- API上の単価は万円／月、DBは円／月として換算

### 3.3 マッチング

- 必須スキル一致率80%＋尚可スキル一致率20%でスキル点を算出
- 単価、稼働形態、開始時期、年齢、商流、外国籍、個人事業主を条件判定
- NGがあれば候補から除外し、WARNING数に応じて1.00／0.90／0.80／0.70の係数を適用
- 勤務地は自動足切りせず参考情報として返す
- スコア順と一致数順で候補を並べる
- 同一案件の表示用グルーピング、判断済み結果の再リンク、経験年数の補完に対応
- 開発時の計測では候補計算はコールド約4.2秒、キャッシュ利用時約0.2秒

スコアの詳細な契約は [Phase 1 API契約](../design/phase1-api-contract.md) を参照する。

### 3.4 スキルマスタ

- 正式名・別名の部分一致検索
- 未登録語を `unknown_terms` に収集
- 登録待ち語の仕分け、マージ、案件・要員データの再照合
- スキル経験年数の補完処理

## 4. データと通信上の注意

- SES系はREST、従来のスキルシート系は既存共通POSTラッパーを使っており、通信方式が混在する
- スキルシート系コード値は数値、SES系は文字列中心で表現が統一されていない
- `PUT /ses/personnel/{id}` は全項目更新のため、省略値を意図せず消さないようフロントで全項目を送る
- ロール変更後は既存セッションに即時反映されないため、対象ユーザーの再ログインが必要
- 一覧のメールJOINは本文も転送するため、件数増加時に最適化余地がある
- 多重起動ガードは単一プロセス内のみ

## 5. 既知の課題・今後の確認

- スキルシート検索をサーバー側へ移し、ページング後の表示範囲だけに絞り込みが効く状態を解消する
- `availableFrom` の不正書式を500ではなく400で返す
- 旧抽出データの商流・開始年月を必要に応じて再抽出する
- 個人事業主可否の判定材料をメンバー側に追加するか判断する
- SES系・スキルシート系のE2Eテストを拡充する
- ロール変更と権限制御を画面経由で継続確認する
- C8（候補者昇格・承認UIの廃止）を実施する場合は、要件、データモデル、API、画面、モックを同時に更新する
