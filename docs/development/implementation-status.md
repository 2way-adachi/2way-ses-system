## 3. 実装済み: 要員・案件・提案・マッチング（`/ses/**`）

実API接続済み。API形式は**REST**（GET/POST/PUT/PATCH、素のaxios）。認証は既存トークンをヘッダー付与。

### 要員（personnel）

- `GET /ses/personnel?type=&q=&status=`、`GET /ses/personnel/{id}`、`POST`、`PUT`、`GET /ses/personnel/{id}/matches`
- 区分: 自社社員/BP。ステータス: 稼働可能/稼働中/稼働不可。保有スキルはskill_id参照＋経験年数
- **2026-08-17拡張**: skill_sheet_id（UNIQUE・1シート1要員）／氏名イニシャル／性別（API文字列）／生年月日を追加。
  希望単価をAPI公開（万円/月。DBは円）。**PUTは全項目送信の非selective更新**（省略項目はクリアされる）
- **登録・編集画面・スキルタグ入力UIも実装済み**（/member/new・/member/:id/edit。サジェスト選択のみ・自由入力不可。
  スキルシートの手動紐付け選択ダイアログ付き）

### 案件

- `GET /ses/projects?q=&status=`、`GET /ses/projects/{id}`、`GET /ses/projects/{id}/candidates`
- 登録・更新APIは意図的に無し（起点はメール取り込み側の将来実装）
- ステータス: open/closed。単価レンジ・リモート区分・開始時期・面談回数等
- **案件一覧画面は削除**（2026-08-17決定。メール取り込み実装後の「案件メール一覧」が同じ `projects` の
  一覧になるため収斂させる）。**案件詳細（候補要員表示付き）はメニュー外で残置**し、
  マッチング一覧・提案・要員詳細からリンクで到達する。一覧APIは残す

### 提案

- `GET /ses/proposals?projectId=&personnelId=&status=&includeDone=`、`POST`、`PATCH`
- ステータス6値: 下書き→提出済み→面談→成約/見送り/取下げ（遷移ガードなし・後戻り自由）。
  提出時刻・結果確定時刻を記録。作成時にスコア・一致/不足スキルを `match_snapshot`（json）へ凍結
- **実施済み（2026-08-17 提案改修）**: ステータスを7値
  （0:下書き/1:提案メール送信済み/2:面談/3:先方返信待ち/4:完了/5:見送り/6:取下げ）へ変更。
  `interview_done_count`・`next_action_date` カラムを追加し、レスポンスに
  `projectTitle`・`projectInterviewCount` を追加（契約不整合も解消）。
  フロントは「面談（2/3回目）」表示・次回アクション日の表示/更新に対応。
  thyme/Lavenderともテスト・型チェック全PASS
- devDBへのALTER適用は**完了**（2026-08-17人間実行。proposals新カラム・matchingsテーブルとも適用を検証済み）。
  移行用ALTERファイルは適用完了に伴い削除し、`docs/ddl/schema-ses.sql`（変更履歴付き）に一本化した

### マッチング

- **新スコア仕様（決定#25）を実装済み（2026-08-18。devDB実機検証済み）**。仕様の正は
  [phase1-api-contract.md](../design/phase1-api-contract.md) マッチング節
- skillScore = 必須スキル一致率×0.8＋尚可一致率×0.2（片側0件はもう片方100%扱い）。必須/尚可は
  project_skills.required で区別し、タグ付けは required_skills_text / preferred_skills_text の
  原文出現で区分（どちらにも出現しない語は必須扱い）。既存データは再照合APIで新区分に収束
- conditionChecks 7軸（単価・稼働形態・開始時期・年齢・商流=OK/WARNING/NG、外国籍・個人事業主=OK/NG）、
  各軸に日本語の理由。単価は対の値が揃えば部分判定（上限のみ記載の案件でも判定）
- NG1件で候補から除外。conditionFactor=1.00/0.90/0.80/0.70、score=skillScore×conditionFactor
  （小数第2位丸め・表示は0〜100点）。ソートはscore降順→一致数降順、上位20件
- match_snapshotはversion付きv2で凍結（既存v1は無移行で従来表示）
- 実装メモ: 要員側の remote_preference・preferred_location は skill_sheets 側のカラムのため
  紐付きスキルシート経由で取得（未紐付けは「判定材料なし」でOK通過）
- フロントは総合点1軸＋内訳テーブル（skillScore×conditionFactor・条件別status/理由・場所参考行）を
  共通コンポーネント matchBreakdown で3画面＋提案控えに表示
- 双方向（案件→候補要員／要員→適合案件）、推薦理由はPhase2のLLM用の席のみ（従来どおり）
- **要員候補（未昇格BP）も評価対象**（決定#31。2026-08-20実装）: staff_candidate_skills でタグ付けし、
  候補側は単価・開始時期・年齢（直接値）・商流/個人事業主（affiliationから導出）で判定。
  稼働形態・外国籍・経験年数は判定材料なし。イニシャル名での自動昇格API（冪等・タグコピー・matchings付け替え）
- **location軸（9軸目）**（決定#34）: 8地方区分辞書で案件の勤務地と要員所在地を突き合わせ。
  否定キーワード最優先→フルリモート例外→低頻度出社はWARNING→特定不能は判定材料なし。`projects.region` に保持
- **同一案件グルーピング**（G1）: タイトル正規化＋勤務地トークン＋単価レンジで `projects.group_id` に付与。
  マッチング母集団は代表1件のみ、承認/見送りはグループ単位で引き継ぎ、結果画面はグループ内の全メールを提示
- **要員候補の名寄せ**（決定#35。2026-08-20実装）: イニシャル＋最寄駅トークン＋年齢で `staff_candidates.group_id`
  に付与。所属はキーに使わない（表記ゆれで割れるため）。マッチング母集団は代表のみ、昇格も代表からのみ可。
  実データ1,047件→439グループ・誤統合0件（[精度検証](../design/20260820_1616_staff-candidate-grouping-accuracy.md)）。
  イニシャルまたは最寄駅が空のレコードは畳まない
- **性能対策**（決定#31）: 共通スキル前置フィルタ・案件の鮮度フィルタ（開始時期が過去/受信1ヶ月超は評価対象外）・
  一覧のサーバ内キャッシュ。実測はマッチング一覧がコールド4.2秒・キャッシュ0.2秒（対策前は数分）
- **運用手順**: relink（全件再照合）は約5秒。ただし required_years が一部失われるため、
  **relink後は skill-years-backfill を続けて実行する**。region・group_id にもバックフィルAPIがある

### スキルマスタ

- `GET /ses/skills?q=` — 正規名＋別名に部分一致のサジェスト。Phase1はシードSQL投入（登録・管理APIなし）

## 4. 実装済み: 営業メール取込（2026-08-17。実IMAP・実LLM接続は未検証）

- **取込バッチ**（thyme）: さくらIMAPS読み取り専用接続→ヘッダ/本文の2段階バッチFETCH→Message-ID重複排除→
  バウンスのみルール除外→残り全部LLM（OpenAI Responses API・Structured Outputs・reasoning effort none）で
  3値分類＋構造化抽出（複数案件/要員の分割、上限年齢含む、要員はイニシャルのみ）→
  mails/projects/staff_candidates 登録＋スキルマスタ照合（未知語は unknown_terms）
- **実行制御**: スケジューラ（enabled/間隔は設定・既定off）＋手動実行API＋プロセス内多重起動ガード。
  履歴は実行ヘッダ（mail_import_runs）＋アカウント別明細の2階層。devDB適用済み
- **設定**: APIキー・IMAP認証はgit管理ymlにプレースホルダのみ（実値は外出しyml/環境変数）
- **リード編集API**: 案件の参照・編集（PUT。単価はAPI万円へ統一）、要員候補の一覧・詳細・編集（確認/非表示）、
  メール原文参照
- **画面**（Lavender）: 案件メール一覧/編集・要員メール一覧/編集を実API化（モック撤去）。
  取り込みボタン＋直近サマリ＋履歴ダイアログ（実行中は直列ポーリング）。編集画面にメール原文カード
- **実結合確認済み（2026-08-17）**: 実IMAP・実OpenAI・開発DBで初回取り込み873通（LLM処理829、
  案件536・要員候補331を登録、17分55秒・429ゼロ・エラーゼロ）。分類・抽出品質は良好、
  要員イニシャルの全件検査で実名混入ゼロ。2回目実行は新着のみ9秒で重複取り込みなし
- 既知の制限: 多重起動ガードはプロセス内のみ／一覧のmails JOINが本文カラムも転送（件数増加時に要最適化）／
  スキルタグ（project_skills）の画面編集は未対応
- **実結合で発見した要対応**:
  1. **スキルマスタ未投入のため project_skills が0件**（スキル語は全て unknown_terms へ。
     上位: AWS 117 / Java 89 / Python 62 / PostgreSQL 55 ほか＝そのままシード素材）。
     シード投入＋既存案件の再紐付けが必要（マッチングの前提）
  2. start_ym の充足13.6%（「即日」「7月〜」の正規化が弱い。プロンプト改善は商流追加〔決定#19〕と
     同時に prompt_version を上げて対応するのが効率的）
  3. kind=project 判定なのに案件0件のメールが12通（要観察）
  4. LLMリトライ待機にログが無く、遅延時の切り分けができない（進捗ログ追加を検討）

## 5. 撤去・差し替え対象（要件変更で不要になった実装）

| 実装 | 経緯・方針 |
|------|------|
| `/skill-sheet/entry` API（thymeスタブ） | **撤去済み**（2026-08-17実施） |
| ログインAPIレスポンスへのロール追加（仮実装。Lavenderのログイン状態・IndexedDBにも保持） | 現在は一覧の勤怠提出元列・検索の表示制御に使用中のため**当面維持**。本認証のロール定義確定時に差し替える |
| サイドバー2大項目構成・`/ses/**` パス体系 | 新メニュー構成（大項目「SES」1つ・`/member` 等）への改修が必要 |

**権限出し分けの意図は消滅ではなく実装箇所が移る（2026-08-17 人間確認）**:
一般ログイン（メンバー）の主目的は**自分のスキルシートの編集**であり、
旧要件の「権限に応じた初期表示出し分け」は、タブ集約後の構成では
「一般ユーザーを自分のメンバー詳細（スキルシートタブ）へ誘導する」形で実装し直す。
一般ユーザーにも案件一覧の参照は許可する（2026-08-17決定。許可範囲は一元管理して切り替え容易にする）。

  整合チェック＋1回リトライの後処理（画面に原文が出るため提案時に人間が気付ける状態ではある）
- ロール・育成画面の**画面経由の実DB結合確認**（API・起動回帰は確認済み。一般アカウント作成→一般ログイン動作の確認が未）
- 既存536案件の商流・start_ymは旧版数(v1)抽出のため未設定/低充足のまま（v2での再抽出は要判断。
  商流NULLは足切りされないため実害は限定的）
- 個人事業主可否のフィルタ適用（要員側に個人事業主区分が無く判定材料不足。personnel区分追加は要判断）
- E2Eテスト（スキルシート系・SES系とも）
