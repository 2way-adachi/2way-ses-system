- [x] **A5. ステージングでSES系APIに「パラメーター不正」WARNが多発** — **完了**（thyme `1666abe`。実害なし・ログノイズのみと確定）
  - **真因は `/ses/**` がREST形式だからではなかった**。Lavenderのses系axiosクライアント（`api/ses/client.ts`）が
    **フラットな `headers` に `Content-Type: application/json` を設定**しており、axios 0.21.1 の仕様で
    `common` でもメソッド別でもないこのヘッダは**GETにも付く**。結果ボディ空のままJSON分岐へ入り、
    Jacksonが `No content to map due to end-of-input` で例外→catchでWARN、という経路だった
  - したがって**方針に書かれていた「`/ses/**` を検査対象から除外」では直らない**（除外してもGETがWARNになる
    構造が残り、FUKURO側にGETを足したときに再発する）。Content-Typeの判定より前にContent-Lengthで
    ボディの有無を見る形にして根本を直した
  - ボディを持つ壊れたJSON・未対応Content-Typeは従来どおりWARNのまま（判定は緩めていない）
  - 副作用として、ボディが空のPOSTは従来のWARNから「ボディなし」のinfoになる。chunked転送のPOSTは
    リクエストログが出なくなる（axiosの通常のJSON POSTはContent-Lengthを付けるため現状は該当なし）
  - `com.fukuro.thyme.RequestFilter:45` が `/it/api/ses/projects`・`/it/api/ses/mail-import/runs` 等に対し
    「パラメーター不正」を**299件**出力している
  - `/ses/**` はREST形式でFUKURO共通の封筒規約を使わないため、RequestFilterの想定と食い違っている可能性。
    レスポンス自体が異常か（実害があるか）はログからは判別できていない
  - 方針: まず実害の有無を確認し、ログノイズのみなら `/ses/**` を検査対象から除外する

- [x] **A6. マッチング結果画面のメールフレームが横スクロールしないと詳細リンクが見えない** — **完了**（Lavender `d75fe09`）
  - 2026-08-20 ステージング実機で発見。タスクリスト外（決定#36の2フレーム化以降の症状）
  - 原因: 件名を包む `<Box flexGrow={1}>` がflexアイテムで既定の `min-width: auto` のため、
    省略表示の指定があっても中身の固有幅までしか縮まず、`nowrap` の長い件名が行を押し広げていた。
    `overflow-y: auto` のとき `overflow-x: visible` は `auto` に計算されるため横スクロールバーが出る
  - `minWidth={0}` を付けて縮小を許可し、省略表示を効かせて横あふれ自体を無くした
    （`overflowX: 'hidden'` で隠す対症療法は採らない。リンクが見えないままになるため）

## L. 案件 region が取込時に付与されない（2026-08-20 発見・2026-08-21 起票）

決定#34（location軸）で追加した `projects.region` の付与経路が `ProjectService.backfillRegions()` だけで、
メール取込のパスに `setRegion` がない（`grep setRegion` の結果は `ProjectService.java:714` の1箇所のみ。
`MatchSubjectData` の2箇所は要員側の都度解決で永続化しない）。
そのため新着案件は常に `region IS NULL` のまま増え続ける。

**実測（2026-08-20 時点）**: 既存1,607件のうち1,178件はバックフィル済みで値が入っているが、
同日09:16の取込で追加された97件は全件NULLだった。

**影響は限定的**: location軸の判定は `resolveProjectRegions()`（`ProjectService.java:719`）が
`location` テキストから都度解決しており、永続値はテキストから解決できなかったときのフォールバックにすぎない。
どちらも解決できない案件は「判定材料なし＝OK」に倒れる設計のため、誤判定は起きない。
フロントは `region` を参照していない（`types.ts`・画面とも参照なし）。

**それでも直す理由**: 「NULLが正常なのか未処理なのか判別できない列」になっている。
要員側は永続列を持たず毎回テキストから解決するため、案件側だけが非対称な状態になっている。

- [ ] **L1. 取込時に region を付与する**
  - `MailImportRecordService.java:556`（`projectService.assignGroup(project)` を呼んでいる位置）の近くで
    region も解決して設定する。`assignGroup` と同じく案件insert直後に行う
  - 解決は `LocationDictionary.resolveRegion(location)` を使う（`backfillRegions` と同じ同期辞書引き。LLMは使わない）。
    複数地名併記で一意に決まらない場合は最初に解決できたものを採用する既存挙動に合わせる
  - 解決できない場合はNULLのままでよい（判定はテキスト側で行われるため実害がない）
  - 手動登録・編集（`ProjectService.update`）でも location が変わりうる。グループ再判定と同じ理由で
    region も再解決するか検討する（`update` は非selectiveの `updateByPrimaryKey` を使うため、
    設定しないとNULLで上書きされる点に注意。決定#35のレビューで同種の事故が出ている）
- [ ] **L2. 検証**
  - 新規取込を1通流し、`projects.region` が入ること
  - 案件の勤務地を編集して保存し、region が消えない・変更後の地方に追従すること
  - `backfillRegions` の既存テストが通ること

**修正セッションは1本にまとめる**（他タスクと同じセッションで対応し、region 単独でセッションを分けない）。

## M. OpenAI呼び出しのレート制御と並列数の見直し（2026-08-21 人間指示・決定#43）

2026-08-19に並列4で429を踏み、暫定で2へ引き下げたまま。**もう少し上げたい**というのが起点。

### 調査済みの前提（推測ではなく実測・コード確認済み）

- **上限を決めているのは並列数ではなくTPM**。実測 TPM 200,000 ÷ 1リクエスト約6,000トークンで
  **毎分約33リクエストが天井**。並列数は「どれだけ速く天井にぶつかるか」を決めるだけで、
  ペーシング無しに並列だけ上げるとバーストが強くなり429を踏む頻度が上がる
- **適正並列数 N = 33 × T ÷ 60**（T = 1リクエストの所要秒数）。
  T=5秒ならN≈3 / T=10秒ならN≈6 / T=20秒ならN≈11。**T が未計測のため現状では決められない**
- 現状のバックオフは**スレッド単位**（`OpenAiMailExtractor.waitBackoff()` が `Thread.sleep`）。
  429を踏んだ1本が待つ間も他スレッドが投げ続けるため、**全体の投入レートが下がらない**。
  2026-08-19にリトライ5回・累計62秒粘って全滅したのはこれが理由
- 並列は `MailImportService` の `Executors.newFixedThreadPool(parallelism)`（固定プール）
- レート制限ヘッダが使える（[OpenAI API仕様](../../../thyme/2way-thyme/docs/api_spec/openai-api.md) §レート制限）:
  `x-ratelimit-remaining-tokens` / `x-ratelimit-reset-tokens` / `Retry-After`。
  仕様書自身が「remaining-tokens を監視して並列数を動的に絞ると429を踏む前に減速できる」と記載

- [ ] **M1. 429時の共有クールダウン** — **未着手**
  - 429を踏んだら「次に投げてよい時刻」を**共有状態**に持ち、全スレッドが送信前にこれを尊重する
  - `Retry-After` は公式の指示どおり**最小待機時間**として扱い、さらに小さなランダム遅延を加える
  - 現状のスレッド単位 `Thread.sleep` を置き換える。`OpenAiMailExtractor` はステートレスに作られているため、
    共有状態の置き場所（Bean化するのか、専用クラスを起こすのか）を決めること
  - 確認: 429を返すモックサーバーに対し、**1本が踏んだ直後に他スレッドが投げないこと**を検証する
    （A4のテストで使ったJDK標準 `HttpServer` の方式が流用できる）
- [ ] **M2. ヘッダ駆動の事前減速** — **未着手**
  - `x-ratelimit-remaining-tokens` が閾値を割ったら `x-ratelimit-reset-tokens` まで全スレッドを待たせる
  - 閾値の起点は「1リクエストの実測トークン × 並列数」を下回ったら止める、程度から
  - **ヘッダは直前のリクエスト時点の値**であり、並列度が高いと取りこぼす。M1が後段の保険になる前提で組む
  - **注意**: api_specに載っている例示値（`x-ratelimit-limit-tokens: 150000` 等）は**サンプルであって実値ではない**。
    必ずヘッダから読むこと。同仕様書はRPM・Batch queueも未検証と明記している
- [ ] **M3. 所要時間とトークン数の計測を仕込む** — **未着手**（M1・M2と同時に実施する）
  - 1リクエストの所要時間と `usage.input_tokens` / `usage.output_tokens` を取込履歴に記録する
  - M4の判断材料。モデルやプロンプトを変えたときの再計測にも使う
  - `reasoning_tokens` も併せて記録すると、`effort: none` が効いているかの監視になる（api_spec §3参照）
- [ ] **M4. 並列数の見直し** — **未着手**（M1〜M3の完了が前提）
  - M3の実測から N = 33 × T ÷ 60 で決め、`ses.mail-import.openai.parallelism` の既定値を更新する
  - **M1・M2が入る前に並列数だけ上げないこと**（バーストが強くなるだけで、429の頻度が上がる）
- [ ] **M5. `application.yml` の設定がgitに入っていない** — **未着手・要判断**
