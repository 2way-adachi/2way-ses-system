## 0. なぜ F1 と同時なのか

F1 が作る地名の前処理（指示書§3.2 の手順1〜6：括弧除去・`※`以降除去・区切り分割・
末尾の`駅`等除去・先頭の路線名除去・8文字超の破棄）が、**本タスクの勤務地判定でそのまま必要**になる。
別々に書くと同じ前処理が2箇所に生まれる。

ただし**出口は違う**。

| | 入力 | 出口 |
|---|---|---|
| F1 location軸 | 勤務地文字列 | トークンを辞書に引いて **8地方区分**（関東・関西…） |
| 本タスク | 勤務地文字列 | **トークン集合そのもの**を突き合わせて一致判定 |

**`region` をグルーピングに使ってはいけない。** 地方粒度では
「UIデザイナー（六本木一丁目・60万）」と「UIデザイナー（外苑前・50万）」がどちらも関東になり、
別案件を1つに畳んでしまう（検証で実在を確認済み）。

そのため F1 の実装では、**前処理でトークン列を返す部分を独立したメソッドとして切り出す**こと。
辞書引きと地方判定はその外側に置く。本タスクはそのトークン列取得だけを呼ぶ。

対象ブランチ: thyme `feature/skill-sheet` / Lavender `Feature/skill-sheet`
着手前に `git status` で現状を確認すること（個人属性移設で `ProjectService` 等が変更済み）。

## 2. 判定ロジック（そのまま実装できる形）

```
同一グループ = タイトル正規化一致
             AND 勤務地トークンが交差（どちらかが空なら条件スキップ）
             AND 単価レンジが1.15倍未満
```

### 2.1 タイトル正規化

```
1. NFKC 正規化
2. 小文字化
3. 次の文字をすべて除去:
   空白全種 - ‐ ― ー ・ / ( ) [ ] 【 】 「 」 * ★ ☆ : , 、 。 ! ? ~ 〜 + &
4. 結果の完全一致で判定
```

これで `SaaS`/`Saas`、全角半角の括弧、`(リーダー)`/`（リーダー）` が吸収される。
検証では9グループが追加統合され、**誤統合はゼロ**だった。

### 2.2 勤務地

F1 の前処理で得たトークン集合どうしを比較する。

```
1. 両者のトークン集合を取得（F1§3.2 手順1〜6。辞書引きはしない）
2. どちらかが空集合 → この条件はスキップ（タイトルと単価で判定する）
3. 交差が1つ以上あれば一致、なければ別グループ
```

「どちらかが空ならスキップ」は実データに合わせた判断。`フルスタックエンジニア` は
`（空）` 2件・`フルリモート` 4件・`恵比寿駅` 3件で、空とフルリモートは同一案件（ともに85万）、
恵比寿は別案件（90万）だった。空を不一致扱いにすると同一案件を割る。単価が防波堤になる。

交差判定にする理由は、同じ案件が `六本木一丁目駅、神谷町駅` と `六本木一丁目駅` のように
片方だけ列挙するケースがあるため。

### 2.3 単価レンジ

```
min同士・max同士を比較する。
片方が NULL の組は比較しない（スキップ）。
いずれかの組で max/min >= 1.15 なら別グループ。
```

同一案件でも表記ブレで 730000/750000 のような差が出る（比1.03で同一と判定される）。
一方 `金融取引システムのハードウェア更改`（西葛西・同名・同勤務地）は
DBA枠90万／RHEL設計枠75万／HPサーバ枠75万の**3ポジション募集**で、比1.20で分離される。

## 3. group_id の採番と合流

### 3.1 照合は「グループ代表」とのみ行う

新しい案件を既存グループへ入れるかは、**グループの代表レコード1件とだけ**照合する。
グループ内の全メンバーと照合して1件でも一致したら合流、という実装にしてはいけない。
単価レンジ条件が推移的でないため（A-B が1.10、B-C が1.10、A-C が1.21）、
グループが芋づる式に膨らんで別案件を飲み込む。

### 3.2 代表レコード = 受信が最新のもの

```
代表 = グループ内で mails.received_at が最大のもの
       received_at が NULL（手動登録）は projects.create_datetime で代用
```

単価や勤務地の記載が更新されている可能性が高い方を正とする。
**新着が合流すると代表が入れ替わる**点に注意（一覧の表示内容も入れ替わる）。

### 3.3 採番

`group_id` は `projects` 内で採番する（`MAX(group_id) + 1`）。専用テーブルは作らない。
同時取り込みの競合は、取り込み処理が単一実行前提のため考慮不要。

## 4. DDL

```sql
ALTER TABLE projects ADD COLUMN group_id INT NULL COMMENT '同一案件グループID';
CREATE INDEX idx_projects_group ON projects(group_id);

ALTER TABLE matchings ADD COLUMN group_id INT NULL COMMENT '同一案件グループID';
CREATE INDEX idx_matchings_group ON matchings(group_id);
```

反映先は4本すべて（F1 と同じ）:
- `thyme/2way-thyme/docs/ddl/schema-ses.sql`
- `lemongrass/src/test/resources/ddl/schema-ses.sql`
- `thyme/src/test/resources/ddl/schema-ses.sql`
- `2way-ses-system/db/phase1_ddl.sql`

**F1 の `projects.region` 追加と同じファイルを触る。ALTER は1回にまとめること。**

`matchings` は現在3件・`proposals` は4件でほぼ空のため、移行コストはほぼゼロ。
既存3件の group_id は、対応する project の group_id をコピーすれば足りる。

## 5. 承認・見送りのグループ単位化（タスク8）

`matchings` の実質キーを `project_id × personnel_id` から **`group_id × personnel_id`** に変える。

- `MatchingService.decision()` は group_id で 1レコードを更新する
- 一覧・結果画面が状態を引くときも group_id で引く
- `project_id` カラムは残す（どの案件を見て判断したかの記録）。ただし判定には使わない
- `proposals.via_mail_id` は現状維持。「どのメール経由で提案したか」は個別メール単位が正しい

これにより「重複28件の案件を1件ずつ見送る」現状の手間がなくなり、
**新着メールが同じグループに合流したときも見送り状態を引き継ぐ**。

## 6. 一覧の畳み込み（タスク6・7）

### 6.1 マッチング計算の母集団（タスク6・性能改善）

`ProjectService.fillFreshOpenProjects()` は `MatchingService.fill()`（マッチング一覧）と
`PersonnelService.matches()`（メンバー詳細マッチングタブ）**両方の起点**。
ここでグループ代表だけを返すようにすると、評価対象が **1,556件 → 619件** になる。

メンバー詳細マッチングタブの都度計算約1.5秒（全案件スキャン×リモートDB）の短縮が見込める。
実測して結果を記録すること。

### 6.2 一覧表示（タスク7）

代表1件を表示し、重複件数を併記する（`VBA開発（現場直：弊社交代枠）` なら 28件）。
行クリックで開く結果画面の右側に、グループ内の全メールが並ぶ（タスク9）。

## 7. 落とし穴

- **バックフィルは受信の古い順に処理する。** 新しい順だと代表が先に確定して合流判定が変わる
- **`region` をグルーピングに使わない**（§0）。F1 の成果物のうち使うのは前処理のトークン列だけ
- **必須スキル文を判定条件に入れない。** 抽出品質が不安定で、片方だけ空のケースが多い。
  条件に入れると同一案件が割れる（検証で40グループ中の大半がこのパターン）
- **タイトルの類似度判定（あいまい一致）を入れない。** Jaccard 0.6〜0.95 の全域で
  真陽性（`…PMO` と `…PMO募集`）と偽陽性（`保守A` と `保守B`、`要員A` と `要員B`）が混在し、
  閾値では分離できない。包含判定も同様に誤爆する
- **グループ代表が入れ替わる**（§3.2）。一覧のソート順や表示内容が新着で変わることを前提に実装する
- 鮮度フィルタ（決定#31）との順序に注意。**鮮度で絞ってから代表を選ぶ**のではなく、
  **代表を選んでから鮮度で絞る**。逆にすると、代表が鮮度落ちしたグループが丸ごと消える
