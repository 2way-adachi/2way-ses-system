# 修正タスクリスト テンプレート

修正・改善タスクを別セッション（別担当）へ引き継ぐためのリスト書式。
発見した側が「調査済みの事実」を書き切り、修正する側が**追加調査なしで着手できる**ことをゴールとする。

- ファイル名: `YYYYMMDD_HHMM_fix-tasks.md`（作成日時プレフィックス）
- 置き場所: 実装リポジトリのルート等、修正セッションが最初に開く場所（機密を含む場合は公開リポジトリに置かない）

---

```markdown
# 修正タスクリスト（YYYY-MM-DD作成・修正用セッション向け）

対象: {リポジトリ}@{ブランチ}（着手基点: コミットIDまたは「コミット済み最新」）
出典: {発見の経緯: 実機確認・レビュー・検査レポートへのリンク等}

## A. バグ（優先）

- [ ] **A1. {症状を1行で}**（発見日・発見方法）
  - 箇所: `{ファイルパス}:{行}` — {原因の説明。コードを読んで確認した事実のみ書く}
  - 方針: {修正方針。既存の類似実装（パターン元）があれば `ファイル:行` で示す}
  - 確認: {修正後に何をどう確認すれば完了と言えるか}

## B. 改善（レビュー指摘・PR前対応など）

- [ ] **B1. {内容}**
  - 箇所: {対象ファイル一覧。横展開系は機械的な走査で対象を確定させ、全件列挙する}
  - 方針: {…}
  - **対象外**: {一括適用してはいけない箇所があれば明記。用語置換・共通化系は特に}

## C. 軽微・任意

- [ ] C1. {内容}（優先度が低い理由も添える）

## D. ドキュメント（コード外）

- [ ] D1. {更新すべき文書と追記内容}

## 進め方メモ

- コミュニケーション: コミット・pushの承認ルール、質問先
- 検証コマンド: {テスト・型チェック等、このリポジトリでの実行方法}
- 完了時: このファイルのチェックボックスを埋め、完了コミットIDを追記する
```

---

## 記入ルール

1. **1タスク = 症状・箇所・方針・確認の4点セット**。根拠のない推測は書かず、コードで確認した事実だけを書く
2. **箇所は `ファイル:行` まで特定**する。横展開タスクは対象を走査で確定し全件列挙（「他にもあるかも」で渡さない）
3. **やってはいけないこと（対象外）を明記**する。一括置換・一括適用系のタスクは特に、除外リストがないと壊される
4. 修正パターンが既存コードにあるなら**パターン元を示す**（新規発明よりも既存踏襲を優先させる）
5. 完了したタスクはチェックを埋めて**対応コミットIDとセッション/担当を追記**し、リストは消さず残す（経緯の記録を兼ねる）
6. 決定・仕様に関わる項目は本リポジトリの `decision-log.md` へ、実装状態は `implementation-status.md` へ反映し、リストからリンクする
